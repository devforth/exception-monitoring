# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Lightweight self-hosted error and log monitoring server that accepts data from the official Sentry SDKs via DSN (envelope protocol). Go, embedded SQLite (`modernc.org/sqlite`, no CGO), shipped mainly as a Docker image (`FROM scratch`, size budget 50 MB, currently ~20 MB, ~6 MB to pull). MIT, public DevForth OSS project. Tracklify task: `DevFo-OSS/17`.

Scope: errors and logs only. Tracing spans, session replay, uptime and `client_report` items are accepted and dropped, not stored.

Stages: 0 protocol research, 1 skeleton, 2 ingest, 3 data model and grouping, 4 REST API, 5 UI (htmx) are done; 6 notifications (Slack and Telegram short, email full) is in progress. Next: 7 retention, 8 packaging and docs, 9 MCP. The REST API is shaped so an MCP server can be layered on it (GlitchTip's MCP tool set is the reference).

## Commands

Go is installed in `~/.local/go`; if `go` is not on PATH, run `export PATH="$HOME/.local/go/bin:$HOME/go/bin:$PATH"` first.

```sh
make test         # go test -race ./...
make lint         # golangci-lint (.golangci.yml): vet, staticcheck, errcheck, gofmt/goimports, wsl blank lines
make fix          # auto-fix formatting, import order and blank lines; run after editing Go code
make build        # static binary to bin/exception-monitoring
make docker       # build image devforth/exception-monitoring:dev
make image-size   # fails if the image is over MAX_IMAGE_MB (50)

go test ./internal/store -run TestNewerSchemaRejected -count=1   # single test
node --check internal/ui/static/app.js                           # Go tests do not run the JS
```

Do not start the server (`make run`, `docker run`, …) yourself; the user runs it in their own terminal. Check it with `curl localhost:8000/health` and ask the user to start it if it is not reachable. `make run` loads `.env` and `.env.local` (gitignored; template in `.env.example`); without `PROJECTS` every event is rejected, which is only visible with `LOG_LEVEL=debug`. `go run` does not rebuild on change: after editing code (templates, CSS and JS are embedded too), the user must restart it.

CI (`.github/workflows/ci.yml`) runs golangci-lint (pinned version), `make test`, an amd64 image build with the size check and an arm64 build.

## Architecture

- `cmd/exception-monitoring/main.go`: loads config, opens the store, binds the listener before logging "server started", graceful shutdown on SIGTERM. The `healthcheck` subcommand is what Docker's HEALTHCHECK calls (no curl in a scratch image).
- `internal/config`: everything comes from env (`PORT`, `DATA_DIR`, `LOG_LEVEL`, `PROJECTS`, `ALLOWED_ORIGINS`, `RATE_LIMIT_PER_MINUTE`, `API_TOKEN`, `ALLOWED_IPS`, `TRUSTED_PROXIES`, `ADMIN_USERNAME`, `ADMIN_PASSWORD`, and the notification settings in `notifications.go`: `PUBLIC_URL`, `NOTIFY_CHANNEL_TYPES`, `SECRET_KEY`, `SMTP_*`, `EMAIL_FROM`, `NOTIFY_RETRY_FOR`, `NOTIFY_KEEP_SENT`, `NOTIFY_KEEP_FAILED`; list values in env are comma-separated strings, parsed once here into slices). `Notifications.ChannelAvailable(type)` says whether a connection type can be created and what is missing (email needs SMTP, Telegram/Slack need `SECRET_KEY`). `Load()` wraps `loadFrom(getenv)` so tests inject a map instead of touching the process env. `config.Projects` has `Find(idOrName)` and `ByID(id)`; use them instead of looping over projects.
- `internal/store`: SQLite with WAL, `busy_timeout`, `foreign_keys`, and `_txlock=immediate`, which prevents "database is locked" on concurrent read-then-write transactions (there is a test for it).
  - Migrations live in the `migrations` slice in `migrate.go`: versions are sequential from 1, each runs in its own transaction, and an applied migration is never edited (add a new one, backfilling existing rows if needed). Startup refuses a database whose schema is newer than the binary.
  - Tables: `issues` (one per `project_id` + `fingerprint`, with status, `event_count`, `first_seen`/`last_seen`), `events` (unique `project_id` + `event_id`, so SDK retries are ignored; full JSON in `payload`; `trace_id`, `span_id`, `parent_span_id`), `logs` (`trace_id`, `span_id`, attributes JSON), `sessions` (UI logins), `notification_outbox` (see notify; its `channel` column is the connection id), `notification_destinations` (where messages go: an email address, lowercase, with `verified`/`verified_at` and the code hash, expiry, attempts and `verify_sent_at`; or a chat with its encrypted secret), `notification_connections` (a rule: name, `destination_id`, all projects, levels, active; reading a connection joins the destination fields) + `notification_connection_projects`. A connection needs a confirmed destination; deleting a connection keeps the destination, so a confirmed address stays confirmed.
  - Times are fixed-width UTC TEXT (`timeFormat`) so they sort as strings; `first_seen`/`last_seen` use the server receive time, not the SDK clock.
  - `SaveEvent` reports `NewIssue`/`Regression` (a resolved issue that happened again goes back to unresolved; ignored stays ignored) for notifications.
  - `IssueFilter` date ranges apply to `DateField`: any event in range (default, an `EXISTS` on events), `first_seen` or `last_seen`.
  - Lists fetch `limit+1` rows; `store.Page` trims them and says whether a next page exists. Use it for new lists.
  - `store` never imports `sentry`: callers map to `NewEvent`/`NewLog`.
- `internal/server`: `net/http` ServeMux with method patterns (`"GET /health"`), wrapped in a request-logging middleware. Built from `server.Options`; depends on small interfaces (`Pinger`, `http.Handler` for ingest, `Routes` for API and UI), so tests use fakes. Mounts ingest (open), `/health` (open), the API wrapped in `protectAPI` (IP allowlist first, then token) and the UI wrapped in `protectUI` (IP allowlist; the UI checks its own login).
- `internal/access`: `ClientIP` (uses `X-Forwarded-For` only when the direct peer is in `TRUSTED_PROXIES`, read right to left), `FromTrustedProxy`, `RequireAllowedIP`, `RequireToken` (constant-time; empty `API_TOKEN` closes the API).
- `internal/httpjson`: `Write`/`Error` for JSON responses (`{"error": ...}`). Ingest keeps its own `writeError` because Sentry SDKs expect `{"detail": ...}` plus `X-Sentry-Error`.
- `internal/api`: REST API under `/api/v1/` (projects, issues list/get/PATCH status/DELETE, issue events, latest event, event by project + event_id, logs, traces). Routes are registered one by one: a `/api/v1/` subtree would overlap `/api/{projectID}/envelope/` and ServeMux panics on overlapping patterns. Lists return `{"items", "next_cursor"}` with opaque cursors (offset for issues, keyset by id for events/logs). `?project=` takes an id or a name; issues also take `since`/`until`/`date_by`. Shaped so MCP tools map onto endpoints one to one.
- `internal/ui`: web UI, server-rendered `html/template` + htmx.
  - Pages in `templates/` are parsed with `layout.html` + `partials.html`; every template gets a `view{Page, LoggedIn, Data}`, so fragments are called with `$`, not `.`. htmx requests get only the fragment they swap (`issue-list`/`issue-rows`, `log-list`/`log-rows`, chosen by `HX-Target` / pagination param).
  - Static files are vendored in `static/` and embedded: htmx 2.0.4 and flatpickr 4.6.13 (MIT), no CDN, works offline. Link them with `{{asset "name"}}`, which adds a content hash (`?v=`): versioned URLs are cached forever, unversioned ones revalidate, so browsers never keep a stale file.
  - Pages are sent with `Cache-Control: no-store` and `Vary: HX-Request` (static files override the cache header), API responses with `no-store`. Login always issues a new session and deletes the one the browser had.
  - Strict CSP (`script-src 'self'`, `style-src 'self'`): no inline scripts, styles or `hx-on`; behavior goes into `static/app.js` (event delegation), htmx indicator styles are disabled via the `htmx-config` meta tag.
  - Login: `ADMIN_USERNAME`/`ADMIN_PASSWORD`, session cookie (`HttpOnly`, `SameSite=Lax`, `Secure` behind HTTPS) whose SHA-256 is stored in `sessions` together with a PBKDF2 fingerprint of the admin credentials (computed once at startup; tests lower the iterations in `export_test.go`), so changing them logs everyone out. Failed logins are limited per client IP; POSTs check `Origin` against `Host` (CSRF); `?next=` and bulk `return` only accept local paths.
  - Issue actions (resolve, ignore, reopen, delete) live only in `actions.go`: `applyIssueAction` serves both the issue page (`POST /issues/{id}/action`) and the list checkboxes (`POST /issues/bulk`). Buttons come from the `issue-action-buttons` partial; every one has `data-confirm`, which app.js turns into a confirmation (`{count}` = checked issues). Add new actions there, not in a page handler.
  - List filters: `filterLinks` (pages.go) builds the links of clickable level/project badges and the "active filters" chips; the filters of each list are described once in `issueFilterFields`/`logFilterFields`. Dates are `from`/`to` (UTC days, inclusive, a reversed range is swapped, pickers stop at today); app.js replaces the native date inputs with one flatpickr range field that keeps writing them. Level lists differ on purpose: `eventLevels` (Sentry, `warning`) and `logLevels` (`warn`, `trace`).
  - Logs are tied to an error by span, not by trace (a browser keeps one trace for the whole tab, so every request from it shares the trace): a log belongs to an event if it has the same `trace_id` and its `span_id` (from the `sentry.trace.parent_span_id` attribute) is the event's `span_id` or `parent_span_id`. Without a span match the issue page falls back to logs of the same trace within a minute of the error and says so.
  - Event details are rendered from the stored payload re-parsed with `sentry.ParseEvent`; stack reading goes through `sentry` methods shared with email.
  - Notifications page (`connections.go`, `notifications.html`, `connection.html`): list, add, edit, send test, delete. The type radio lists every type, unavailable ones disabled with the missing setting; app.js shows only the fields of the selected type. Email: the form starts with the address and a Verify button, the rest (`fieldset.connection-rest`) is disabled; htmx swaps the `email-step` fragment (rendered with `renderPartial`) through `POST /notifications/email/start|resend|confirm|change`: an address confirmed before is accepted at once, otherwise a 6-digit code is mailed (hash tied to the destination id, valid 15 minutes, `resendCooldown` 30s between codes, `ui.SetResendCooldown` in tests); a confirmed step carries `data-verified`, which unlocks the rest. Saving requires the confirmed `destination_id`. The address of an existing email connection cannot change (its step is `Fixed`: no "Change email"); if it is not confirmed, its page offers "Send a code" and keeps the rest locked; chat tokens can be replaced, an empty field keeps the stored one. Test messages to unconfirmed addresses are refused. One connection per address, chat or webhook (`findDuplicate` compares `destinationKey`, chat secrets decrypted since their ciphertext differs every time); the error links to the existing connection.
- `internal/sentry`: the SDK wire format only (envelope splitting, `Event`, `Log`), no HTTP or storage. Decoding is deliberately lenient: custom types (`Timestamp`, `Message`, `Tags`, `ExceptionList`, …) accept every shape the protocol allows and fall back to the zero value on an unexpected one, because losing a field is better than losing the error report. `Event.Raw` keeps the full payload; `Event.Trace()` gives trace and span IDs; `NormalizeEventID` turns UUID form into 32 hex.
- `internal/grouping`: decides which events are one issue. Custom SDK `fingerprint` wins (`{{ default }}` expands to the default). Default: exception chain types + in-app frames as file/module + function + source line (`context_line`), no line numbers (JS names `handler: () => {}` after the property, so the function name alone merges unrelated errors); anonymous functions without source use the line number; file and module paths drop origins, query strings (`tsx watch` adds `?<timestamp>`) and bundle hashes; if no frame has source code (browser), the normalized error text is added. Messages group by text with numbers/UUIDs/hex replaced. The package comment documents the rules; change grouping only with tests, because a change regroups new events into new issues.
- `internal/secret`: AES-256-GCM `Box` keyed by `SECRET_KEY` (SHA-256 of the string); encrypts chat tokens and webhook URLs stored in the database.
- `internal/notify`: alerts about new and regressed issues (`SaveEvent` reports them; `StoreSink` calls `Notify` with the project id). Destinations are **connections** stored in the database and managed on the UI Notifications page: type (email/telegram/slack), address or encrypted secret, projects (or all, including future ones), levels, active. Delivery goes through the `notification_outbox` table, so it survives restarts and outages:
  - `Notify` only queues in memory and never blocks ingest. A dispatcher goroutine reads the connections, sends each notification to those that match (`matches`: active, verified, project, level; unknown levels count as errors), applies the flood limit per connection (5 per minute individually, the rest as one `Summary` when the window ends) and writes outbox rows.
  - One worker goroutine per connection (started on demand, and at startup for connections with pending rows) sends due rows in order, so a destination stuck in retries (an SMTP provider rate-limiting; the free Mailtrap sandbox takes about one email per few seconds) does not delay the others. The channel is rebuilt from the stored connection for every attempt, so UI edits apply to queued messages; a disabled or deleted connection fails them (`errGone`). Retries follow `Schedule` (2s, 10s, 30s, 1m, 5m, 15m, 30m, then hourly) until `NOTIFY_RETRY_FOR`; `RetryAfterError` carries a channel's own rate-limit delay. Every failed attempt is logged as a warning, giving up as an error.
  - A cleanup goroutine deletes sent rows after `NOTIFY_KEEP_SENT` and failed ones after `NOTIFY_KEEP_FAILED`.
  - `Close` on shutdown writes the in-memory queue and pending summaries to the outbox and sends what is due; rows waiting for a retry are sent after the next start. Only a killed process loses the in-memory part.
  - `Factory` builds channels from connections (decrypting secrets with the `Box`), sends test messages (`SendTest`) and is shared with the UI. Channels implement `Send`/`SendSummary`: `Slack` (incoming webhook, `{"text"}`, also Mattermost/Rocket.Chat), `Telegram` (bot API, HTML parse mode; errors must not include the URL, it holds the token) and `Email` (plain SMTP via net/smtp, no provider SDK: STARTTLS, or TLS on port 465; multipart text + HTML from `templates/email.html`, styles inline for mail clients; `SendVerificationCode` for new addresses). The full event travels as its original JSON (`event_payload`) and is re-parsed for email. Short formats share `format.go`; stack reading uses `sentry` methods (`OutermostFirst`, `NewestFirst`, `IsInApp`, `SourceLines`) like the UI does. Tests use fake HTTP and SMTP servers (`fixtures.FakeSMTP`) and a real database; assertions do not depend on timing (`waitFor`).
- `internal/agentprompt`: `Build` writes a prompt that asks a coding agent to reproduce and explain an error with evidence, without changing code (the developer checks it and asks for the fix), shared by the issue page ("Prompt" button, copied by app.js) and email notifications (attached as `<project>-<level>-<issue id>.md`, e.g. `backend-error-6.md`: mail clients run no script, so it cannot be copied by a button there). It leaves the server, so it is built from an allowlist (exception chain, frames with source of in-app code, message, request method + path, runtime/os/browser names, breadcrumbs, non-sensitive tags, related log bodies, issue history), never from the raw event; kept free text goes through `redact` (IPs, URL hosts, emails, credentials, JWTs, home directories → placeholders). `prompt_test.go` lists what must never leak; extend it when adding a field.
- `internal/scrub`: removes credentials from SDK payloads before they are parsed or stored (ingest calls it), so the panel, the API, notifications and the database never hold the session cookies or tokens of the monitored app's users. Key-name based (`IsSensitiveKey`: password, token, auth, cookie, session, api key, …; `[name, value]` pairs too; log attributes keep their `{value, type}` shape) plus Bearer/Basic credentials and sensitive query parameters in strings. Data stored before it existed is not rewritten.
- `internal/ingest`: `POST /api/{projectID}/envelope/`. Order matters: CORS → public key (query `sentry_key`, `X-Sentry-Auth`/`Authorization`, or the envelope header `dsn` when sent via a tunnel) → project auth → per-project rate limit → read/decompress body (gzip, deflate; 20 MB cap before and after decompression) → `scrub.JSON` on every event and log item → parse all items → `Sink`. All items are parsed before anything is stored, so a malformed item rejects the whole envelope. Only `event` and `log` items reach the `Sink`; other types are dropped. `StoreSink` computes the grouping fingerprint and maps Sentry types to `store.NewEvent`/`store.NewLog`. Rejections are logged at debug level (ingest is public, so warn-level logging would be a flood vector).

### Projects and DSNs

`PROJECTS=1:backend:<key>,2:frontend:<key>` — `id:name:public_key`. IDs are chosen by the user and must stay stable: the id is part of the DSN (`http://<key>@host:8000/<id>`) and is stored with every event, so it must never be derived from list order. Each service (backend, SSR, frontend…) gets its own project; all live in one container and the UI shows which project an error came from. The Projects page shows each DSN.

Auth model: one admin from env (UI) and an API token, plus an IP allowlist for the UI and API; the ingest endpoint stays open (protected only by DSN keys, CORS `ALLOWED_ORIGINS` and rate limiting) because browsers send errors directly.

### Test data and tools

- `docs/sentry-protocol.md`: notes on the envelope format as actually sent by Sentry SDK 11 (Node and browser): auth via `sentry_key` query or `X-Sentry-Auth` header, missing/`text/plain` Content-Type, item types, log batches, cause chains (innermost first), `fingerprint`, `trace_id`.
- `internal/fixtures` also has `FakeSMTP` (records every session) and `ParseEmail`/`ReadEmail` (with attachments) for tests that check sent mail.
- `testdata/envelopes/*.envelope` + `*.request.json`: real, sanitized SDK captures. Tests read them only through `internal/fixtures`: `All`, `Load`, `Envelope`, `Request.HTTP()` (the request exactly as the SDK sent it), `Projects()` and the keys `BackendKey`/`BrowserKey`/`BackendEnvelopeURL` the fixtures were recorded with. `sentry` and `grouping` tests parse fixtures; `ingest`, `api` and `ui` tests replay every recorded request through the server. A new fixture is picked up automatically.
- `api_test.go` and `ui_test.go` run the full server on a temp database; `ui_test.go` drives it like a browser (login, forms, htmx headers) and sends server logs to `t.Log`.
- `tools/envelope-dumper/dumper.mjs`: Node research server that writes incoming envelopes to `envelopes/` (gitignored).
- `../sentry-playground`: separate AdminForth app used as the test client (not in this repo, not under git). `/api/debug-sentry/` (also "Sentry tests" in its sidebar) has a button per scenario: unhandled/handled errors, cause chains, messages of every level, logs, bursts, background errors, an app crash.

## Conventions

- Tests sit next to the code (`*_test.go`, same package unless they drive the whole server); fixtures go in `testdata/`. When adding a check, make sure the test fails without the fix.
- Blank lines (enforced by `wsl` in `.golangci.yml`, same rule as the team's TypeScript projects): always a blank line before `if`/`for`/`switch`/`defer`/`return`, including `if err != nil` right after the call; consecutive assignments stay together. Run `make fix` after editing; `--fix` only adds blank lines, it never removes extra ones.
- Everything in the repo is in English: code, comments, test data, UI text. Test values are plain and conventional (`root` / `root-password`, `admin`), not invented strings in other languages.
- Use descriptive variable names (`settings`, `database`, `transaction`, `migrationList`), not one-letter ones. Keep the standard Go idioms `err`, `ctx`, `t`, and `w`/`r` in HTTP handlers.
- Do not copy code from Bugsink (PolyForm Shield license) or Sentry (FSL). GlitchTip (MIT) is fine as a reference.
- Commit messages: one subject line containing `DevFo-OSS/17`, no body, no AI attribution. Commit only when asked.
- Keep the README abstract (goals and features). Implementation details are added only once the corresponding stage lands.

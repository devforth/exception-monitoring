# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Lightweight self-hosted error and log monitoring server that accepts data from the official Sentry SDKs via DSN (envelope protocol). Go, embedded SQLite (`modernc.org/sqlite`, no CGO), shipped mainly as a Docker image (`FROM scratch`, size budget 50 MB, currently ~20 MB, ~6 MB to pull). MIT, public DevForth OSS project. Tracklify task: `DevFo-OSS/17`.

Scope: errors and logs only. Tracing spans, session replay, uptime and `client_report` items are accepted and dropped, not stored.

Stages: 0 protocol research, 1 skeleton, 2 ingest, 3 data model and grouping, 4 REST API, 5 UI (htmx) and 6 notifications (Slack and Telegram short, email full) are done; 7 retention is in progress. Next: 8 packaging and docs, 9 MCP. The REST API is shaped so an MCP server can be layered on it (GlitchTip's MCP tool set is the reference).

## Commands

Go is installed in `~/.local/go`; if `go` is not on PATH, run `export PATH="$HOME/.local/go/bin:$HOME/go/bin:$PATH"` first.

```sh
make test         # go test -race ./...
make lint         # golangci-lint (.golangci.yml): vet, staticcheck, errcheck, gofmt/goimports, wsl blank lines
make fix          # auto-fix formatting, import order and blank lines; run after editing Go code
make build        # static binary to bin/exception-monitoring
make docker       # build image devforth/exception-monitoring:dev
make image-size   # fails if the image is over MAX_IMAGE_MB (50)

go test ./internal/store -run TestNewerSchemaRejected -count=1   # single test
node --check internal/ui/views/static/app.js                     # Go tests do not run the JS
```

Do not start the server (`make run`, `docker run`, …) yourself; the user runs it in their own terminal. Check it with `curl localhost:8000/health` and ask the user to start it if it is not reachable. `make run` loads `.env` and `.env.local` (gitignored; template in `.env.example`); without `PROJECTS` every event is rejected, which is only visible with `LOG_LEVEL=debug`. `go run` does not rebuild on change: after editing code (templates, CSS and JS are embedded too), the user must restart it.

CI (`.github/workflows/ci.yml`) runs golangci-lint (pinned version), `make test`, an amd64 image build with the size check and an arm64 build.

## Architecture

- `cmd/exception-monitoring/main.go`: loads config, opens the store, binds the listener before logging "server started", graceful shutdown on SIGTERM. The `healthcheck` subcommand is what Docker's HEALTHCHECK calls (no curl in a scratch image).
- `internal/config`: everything comes from env (`PORT`, `DATA_DIR`, `LOG_LEVEL`, `PROJECTS`, `ALLOWED_ORIGINS`, `RATE_LIMIT_PER_MINUTE`, `API_TOKEN`, `ALLOWED_IPS`, `TRUSTED_PROXIES`, `ADMIN_USERNAME`, `ADMIN_PASSWORD`, and the notification settings in `notifications.go`: `PUBLIC_URL`, `NOTIFY_CHANNEL_TYPES`, `SECRET_KEY`, `SMTP_*`, `EMAIL_FROM`, `NOTIFY_RETRY_FOR`, `NOTIFY_KEEP_SENT`, `NOTIFY_KEEP_FAILED`; levels to record in `recording.go`: `RECORD_EVENT_LEVELS` (default error,fatal), `RECORD_LOG_LEVELS` (default all; `nil` list = every level, empty = none); retention in `retention.go`: `RETENTION_EVENTS`, `RETENTION_LOGS`, `RETENTION_EVENTS_PER_ISSUE`, `RETENTION_LOGS_PER_MESSAGE`, `RETENTION_ISSUES`, `MAX_DATABASE_SIZE` ("2GB"), 0 turns a limit off; list values in env are comma-separated strings, parsed once here into slices). `Notifications.ChannelAvailable(type)` says whether a connection type can be created and what is missing (email needs SMTP, Telegram/Slack need `SECRET_KEY`). `Load()` wraps `loadFrom(getenv)` so tests inject a map instead of touching the process env. `config.Projects` has `Find(idOrName)` and `ByID(id)`; use them instead of looping over projects. Code that needs the projects takes a `config.ProjectList` (`List()`) and asks on every use, because projects change while the server runs; a fixed `config.Projects` satisfies it in tests.
- `internal/store`: SQLite with WAL, `busy_timeout`, `foreign_keys`, and `_txlock=immediate`, which prevents "database is locked" on concurrent read-then-write transactions (there is a test for it).
  - Migrations live in the `migrations` slice in `migrate.go`: versions are sequential from 1, each runs in its own transaction, and an applied migration is never edited (add a new one, backfilling existing rows if needed). Startup refuses a database whose schema is newer than the binary.
  - Tables: `issues` (one per `project_id` + `fingerprint`, with status, `event_count`, `first_seen`/`last_seen`), `events` (unique `project_id` + `event_id`, so SDK retries are ignored; full JSON in `payload`; `trace_id`, `span_id`, `parent_span_id`), `logs` (`trace_id`, `span_id`, attributes JSON), `sessions` (UI logins), `notification_outbox` (see notify; its `channel` column is the connection id), `notification_destinations` (where messages go: an email address, lowercase, with `verified`/`verified_at` and the code hash, expiry, attempts and `verify_sent_at`; or a chat with its encrypted secret), `notification_connections` (a rule: name, `destination_id`, all projects, levels, active; reading a connection joins the destination fields) + `notification_connection_projects`. A connection needs a confirmed destination; deleting a connection keeps the destination, so a confirmed address stays confirmed.
  - Times are fixed-width UTC TEXT (`timeFormat`) so they sort as strings; `first_seen`/`last_seen` use the server receive time, not the SDK clock.
  - `SaveEvent` reports `NewIssue`/`Regression` (a resolved issue that happened again goes back to unresolved; ignored stays ignored) for notifications.
  - `IssueFilter` date ranges apply to `DateField`: any event in range (default, an `EXISTS` on events), `first_seen` or `last_seen`. Only the API exposes the choice (`date_by`); the UI always uses any event in range (the sort already says which date matters).
  - API lists fetch `limit+1` rows; `store.Page` trims them and says whether a next page exists (cursor pagination). UI lists use pages instead: `IssueFilter`/`LogFilter` build their WHERE once (`where()`), shared by `ListIssues`/`ListLogs` and `CountIssues`/`CountLogs`.
  - `store` never imports `sentry`: callers map to `NewEvent`/`NewLog`.
- `internal/server`: `net/http` ServeMux with method patterns (`"GET /health"`), wrapped in a request-logging middleware. Built from `server.Options`; depends on small interfaces (`Pinger`, `http.Handler` for ingest, `Routes` for API and UI), so tests use fakes. Mounts ingest (open), `/health` (open), the API wrapped in `protectAPI` (IP allowlist first, then token) and the UI wrapped in `protectUI` (IP allowlist; the UI checks its own login).
- `internal/access`: `ClientIP` (uses `X-Forwarded-For` only when the direct peer is in `TRUSTED_PROXIES`, read right to left), `FromTrustedProxy`, `RequireAllowedIP`, `RequireToken` (constant-time; empty `API_TOKEN` closes the API).
- `internal/httpjson`: `Write`/`Error` for JSON responses (`{"error": ...}`). Ingest keeps its own `writeError` because Sentry SDKs expect `{"detail": ...}` plus `X-Sentry-Error`.
- `internal/api`: REST API under `/api/v1/` (projects, issues list/get/PATCH status/DELETE, issue events, latest event, event by project + event_id, logs, traces). Routes are registered one by one: a `/api/v1/` subtree would overlap `/api/{projectID}/envelope/` and ServeMux panics on overlapping patterns. Lists return `{"items", "next_cursor"}` with opaque cursors (offset for issues, keyset by id for events/logs). `?project=` takes an id or a name; issues also take `since`/`until`/`date_by`. Shaped so MCP tools map onto endpoints one to one.
- `internal/ui`: web UI, server-rendered `html/template` + htmx. One source for each type: every view type (page data, rows, forms) is defined once, in `contracts`. Sub-packages by role (imports go down this list, never up):
  - `ui` (root): only the composition root, `New` (same signature as before) and `Register`; `export_test.go` holds the test hooks (`services.CredentialsIterations`, `ui.SetResendCooldown`).
  - One rule for data access: controllers never use `store` (the `Controllers` struct has no store field, so the compiler enforces it): all data access goes through services, and a change of several steps (a chat destination plus its connection, a replaced secret plus the save, find-or-create an email destination) is one service method.
  - `helpers`: pure formatting, no HTTP (`TimeAgo`, `LevelClass`, `CleanLog`, `PrettyJSON`, `KeptFor`, `RetentionDifferences`, …); imported by all.
  - `lists`: list machinery shared by pages and templates: `CleanListQuery`, `FilterLinks` and chips, `Badge` builders, `Picker`/`Option`, `Pager`/`ReadPaging`, `DateRange`, levels highest first (`EventLevels`, `LogLevels`).
  - `contracts`: view types and their display methods (`IssuesData`, `IssueData`, `LogsData`, `ProjectView`, `ConnectionView`, `EmailStep`, `DeliveriesView`, `LoginData`, `RequestInfo`, …); imports only `lists` and `helpers`.
  - `views`: embeds `views/templates` and `views/static`, the FuncMap (keys are what templates call), asset versions, the page wrapper `view` and `Renderer` (`Render`, `RenderFragment`, `RenderPartial`, `ServerError`). It takes the project colors as a small interface (`views.ProjectColors`, satisfied by `projects.Registry`).
  - `presenters`: store/config values → `contracts` types, no I/O (no store, no services): issue/log/delivery rows, `Connections` (list rows with status, the form and its email step state, the form shown again, defaults of a new connection), `Projects` (table rows, the form with level options and retention placeholders), `Storage`. Read-only settings come as fields (notification settings, retention/recording defaults, `ProjectName`, `FromEnv`, `Color`), so tests build them from plain values.
  - `services`: non-HTTP logic and every database access of the pages: `Auth` (sessions, credentials fingerprint, `Login` returning `LoginOK`/`LoginWrongCredentials`/`LoginBlocked` with the login limit inside, `IsHTTPS`), `Issues` (list/count/get, recent events, `SelectedEvent`, actions, related logs, agent prompt), `Logs` (list/count, issues of logs), `Projects` (names, DSN, color, unresolved counts, database size), `Connections` (list, delivery health, get, `Create`/`Update`/`SetActive`/`Delete`, duplicates, default names), `Deliveries` (the outbox for the delivery log), `Verification` (email destinations, codes, `ResendCooldown`). Package tests use a real temp database.
  - `requests`: reading the request: forms (project, connection, `ReadChatSecret` returning a `ChatSecret` result, bulk issue IDs), `IsHTMX`, `SafeNext` (local redirect targets only).
  - `middleware`: `RequireLogin`, `SameOrigin`, `SecurityHeaders`, `StaticCache`.
  - `controllers`: the handlers, HTTP only (read the request via requests, call services, build the view with presenters, render), one file per page (`issues.go`, `actions.go`, `logs.go`, `projects.go`, `connections.go`, `email.go`, `deliveries.go`, `auth.go`, `assets.go`) on one `Controllers` struct.
  - `routes`: the route table in two groups: `public` (login, logout) and `dashboard` (`RequireLogin` applied once to the whole group); every POST of any group gets `SameOrigin` (CSRF) automatically, so new routes cannot forget either.
  - Pages below a list link back with the `back` partial (`{{template "back" (back "/projects" "Projects")}}`); app.js follows it on Esc unless a dropdown, dialog or date picker is open or a field has focus.
  - `layout.html`: the menu is a sticky sidebar on the left (a bar at the top under 800px wide, icons only), the page beside it. The toggle collapses it to icons; app.js stores the choice in the `em_sidebar` cookie and the server renders the next page that way (`view.SidebarCollapsed`), so it does not jump on load.
  - Pages in `views/templates/` are parsed with `layout.html` + `partials.html`; every template gets a `view{Page, LoggedIn, Data}`, so fragments are called with `$`, not `.`. htmx requests get only the fragment they swap (`issue-list`, `log-list`, chosen by `HX-Target`). Lists are paged (`lists/pager.go`): `?page=N&per_page=20|50|100` (default 20), the `per-page` select is in the filter form, the `pager` partial under the list ("21–40 of 134", prev/next, numbers around the current page) swaps only the list; filter links and filter changes start from page 1, "Clear all" keeps only the page size, a page past the end shows the last one.
  - Static files are vendored in `views/static/` and embedded: htmx 2.0.4 and flatpickr 4.6.13 (MIT), no CDN, works offline. Link them with `{{asset "name"}}`, which adds a content hash (`?v=`): versioned URLs are cached forever, unversioned ones revalidate, so browsers never keep a stale file.
  - Pages are sent with `Cache-Control: no-store` and `Vary: HX-Request` (static files override the cache header), API responses with `no-store`. Login always issues a new session and deletes the one the browser had.
  - Strict CSP (`script-src 'self'`, `style-src 'self'`): no inline scripts, styles or `hx-on`; behavior goes into `views/static/app.js` (event delegation), htmx indicator styles are disabled via the `htmx-config` meta tag.
  - Login: `ADMIN_USERNAME`/`ADMIN_PASSWORD`, session cookie (`HttpOnly`, `SameSite=Lax`, `Secure` behind HTTPS) whose SHA-256 is stored in `sessions` together with a PBKDF2 fingerprint of the admin credentials (computed once at startup; tests lower the iterations in `export_test.go`), so changing them logs everyone out. Failed logins are limited per client IP; POSTs check `Origin` against `Host` (CSRF); `?next=` and bulk `return` only accept local paths.
  - Issue actions (resolve, ignore, reopen, delete) live only in `services.Issues.ApplyAction` (handlers in `controllers/actions.go`), which serves both the issue page (`POST /issues/{id}/action`) and the list checkboxes (`POST /issues/bulk`). Buttons come from the `issue-action-buttons` partial; every one has `data-confirm`, which app.js turns into a confirmation (`{count}` = checked issues). Add new actions there, not in a page handler.
  - List URLs can be edited by hand: `lists.CleanListQuery` first keeps only the parameters a list understands with valid values (known projects by name, known levels, valid status/sort/dates/page/per_page, search capped at 200 characters), and the query, filter fields, chips and links are all built from that cleaned query; add new list parameters there. Bulk actions take at most 1000 issues.
  - List filters: the fields shared by the issue and log lists are partials (`picker` for the multi-selects, `date-range`, `per-page`, `pager`, `active-filters`; both ends of the date range are one chip, `datesChip`; the sort order is a chip too); `lists.FilterLinks` builds the links of clickable level/project badges and the "active filters" chips; the filters of each list are described once in `issueFilterFields`/`logFilterFields` (`lists/filters.go`). Dates are `from`/`to` (UTC days, inclusive, a reversed range is swapped, pickers stop at today); app.js replaces the native date inputs with one flatpickr range field that keeps writing them. Level names differ on purpose (the Sentry protocol): events use `config.Levels` (`warning`), logs `config.LogLevels` (`warn`, `trace`); the UI lists them highest first (`lists.EventLevels`, `lists.LogLevels`).
  - Logs are tied to an error by span, not by trace (a browser keeps one trace for the whole tab, so every request from it shares the trace): a log belongs to an event if it has the same `trace_id` and its `span_id` (from the `sentry.trace.parent_span_id` attribute) is the event's `span_id` or `parent_span_id`. Without a span match the issue page falls back to logs of the same trace within a minute of the error and says so.
  - Issue page order: header, then the selected event's facts and exception (or message), the issue's events, then the rest of the event (related logs, breadcrumbs, request, tags, contexts, raw JSON). Every table there sits in a `.table-scroll` box (max 420px high, sticky header), so long lists scroll inside it. The trace ID links to `/logs?trace_id=` only when the trace has logs (`services.Issues.TraceLogs`).
  - Event details are rendered from the stored payload re-parsed with `sentry.ParseEvent`; stack reading goes through `sentry` methods shared with email.
  - Notifications page (`controllers/connections.go` and `email.go`, `notifications.html`, `connection.html`): list, add, edit, send test, delete. The type radio lists every type, unavailable ones disabled with the missing setting; app.js shows only the fields of the selected type. Email: the form starts with the address and a Verify button, the rest (`fieldset.connection-rest`) is disabled; htmx swaps the `email-step` fragment (rendered with `RenderPartial`) through `POST /notifications/email/start|resend|confirm|change`: an address confirmed before is accepted at once, otherwise a 6-digit code is mailed (hash tied to the destination id, valid 15 minutes, `services.ResendCooldown` 30s between codes, `ui.SetResendCooldown` in tests); a confirmed step carries `data-verified`, which unlocks the rest. Saving requires the confirmed `destination_id`. The address of an existing email connection cannot change (its step is `Fixed`: no "Change email"); if it is not confirmed, its page offers "Send a code" and keeps the rest locked; chat tokens can be replaced, an empty field keeps the stored one. Test messages to unconfirmed addresses are refused. "Include Open issue link" (`hide_issue_link`) is on by default for email and off for Slack/Telegram (a chat may be public; app.js switches the default with the type until the box is set by hand); `Factory.Channel` wraps the channel in `withoutIssueLinks`, so every channel type drops the links the same way. The delivery log (`/notifications/log`, `controllers/deliveries.go`) lists the outbox newest first with status, attempts and last error, filtered by connection and status (`services.Deliveries`, `notify.Describe` reads a message for display); the notifications list has a Delivery column from `services.Connections.DeliveryHealth` (failing when messages wait for a retry or the latest outcome was an error). The name is optional: an empty one becomes the part of the address before "@", the Telegram chat title (`Factory.TelegramChatTitle`, Bot API `getChat`; falls back to "Telegram <chat id>") or "Slack" (a webhook does not tell its channel); app.js shows it as the placeholder. One connection per address, chat or webhook (`services.Connections.FindDuplicate` compares `destinationKey`, chat secrets decrypted since their ciphertext differs every time); the error links to the existing connection.
- `internal/sentry`: the SDK wire format only (envelope splitting, `Event`, `Log`), no HTTP or storage. Decoding is deliberately lenient: custom types (`Timestamp`, `Message`, `Tags`, `ExceptionList`, …) accept every shape the protocol allows and fall back to the zero value on an unexpected one, because losing a field is better than losing the error report. `Event.Raw` keeps the full payload; `Event.Trace()` gives trace and span IDs; `NormalizeEventID` turns UUID form into 32 hex.
- `internal/grouping`: decides which events are one issue. Custom SDK `fingerprint` wins (`{{ default }}` expands to the default). Default: exception chain types + in-app frames as file/module + function + source line (`context_line`), no line numbers (JS names `handler: () => {}` after the property, so the function name alone merges unrelated errors); anonymous functions without source use the line number; file and module paths drop origins, query strings (`tsx watch` adds `?<timestamp>`) and bundle hashes; if no frame has source code (browser), the normalized error text is added. Messages group by text with numbers/UUIDs/hex replaced. The package comment documents the rules; change grouping only with tests, because a change regroups new events into new issues.
- `internal/secret`: AES-256-GCM `Box` keyed by `SECRET_KEY` (SHA-256 of the string); encrypts chat tokens and webhook URLs stored in the database.
- `internal/notify`: alerts about new and regressed issues (`SaveEvent` reports them; `StoreSink` calls `Notify` with the project id). Destinations are **connections** stored in the database and managed on the UI Notifications page: type (email/telegram/slack), address or encrypted secret, projects (or all, including future ones), levels, active. Delivery goes through the `notification_outbox` table, so it survives restarts and outages:
  - `Notify` only queues in memory and never blocks ingest. A dispatcher goroutine reads the connections, sends each notification to those that match (`matches`: active, verified, project, level; unknown levels count as errors), applies the flood limit per connection (5 per minute individually, the rest as one `Summary` when the window ends) and writes outbox rows.
  - One worker goroutine per connection (started on demand, and at startup for connections with pending rows) sends due rows in order, so a destination stuck in retries (an SMTP provider rate-limiting; the free Mailtrap sandbox takes about one email per few seconds) does not delay the others. The channel is rebuilt from the stored connection for every attempt, so UI edits apply to queued messages; a disabled or deleted connection fails them (`errGone`). Retries follow `Schedule` (2s, 10s, 30s, 1m, 5m, 15m, 30m, then hourly) until `NOTIFY_RETRY_FOR`; `RetryAfterError` carries a channel's own rate-limit delay. Saving an active connection in the UI makes its waiting messages due at once (`store.RetryOutboxNow`, called from `services.Connections`), since a save is usually the fix; a "Retry now (N)" button (`retry-now` partial, `POST /notifications/{id}/retry`) does the same without a save, on the notifications list and the connection page while messages wait for a retry; the worker picks them up on its next poll (`PollInterval`, 1s). Every failed attempt is logged as a warning, giving up as an error.
  - A cleanup goroutine deletes sent rows after `NOTIFY_KEEP_SENT` and failed ones after `NOTIFY_KEEP_FAILED`.
  - `Close` on shutdown writes the in-memory queue and pending summaries to the outbox and sends what is due; rows waiting for a retry are sent after the next start. Only a killed process loses the in-memory part.
  - `Factory` builds channels from connections (decrypting secrets with the `Box`), sends test messages (`SendTest`) and is shared with the UI. Channels implement `Send`/`SendSummary`: `Slack` (incoming webhook, `{"text"}`, also Mattermost/Rocket.Chat; or a bot: `SlackSecret.BotToken` + `Channel` posts through `chat.postMessage` and puts the agent prompt as a code block in a thread under each error, since a webhook does not return the message timestamp; a failed thread post is dropped so the message is not sent twice; `Factory.SlackURL` points to a fake API in tests), `Telegram` (bot API, HTML parse mode; errors must not include the URL, it holds the token) and `Email` (plain SMTP via net/smtp, no provider SDK: STARTTLS, or TLS on port 465; multipart text + HTML from `templates/email.html`, styles inline for mail clients; `SendVerificationCode` for new addresses). The full event travels as its original JSON (`event_payload`) and is re-parsed for email. Short formats share `format.go`; stack reading uses `sentry` methods (`OutermostFirst`, `NewestFirst`, `IsInApp`, `SourceLines`) like the UI does. `Factory.TelegramURL` points to a fake Telegram API in tests (the UI test server has one, so no test reaches api.telegram.org). Tests use fake HTTP and SMTP servers (`fixtures.FakeSMTP`) and a real database; assertions do not depend on timing (`waitFor`).
- `internal/agentprompt`: `Build` writes a prompt that asks a coding agent to reproduce and explain an error with evidence, without changing code (the developer checks it and asks for the fix), shared by the issue page ("Prompt" button, copied by app.js) and email notifications (attached as `<project>-<level>-<issue id>.md`, e.g. `backend-error-6.md`: mail clients run no script, so it cannot be copied by a button there). It leaves the server, so it is built from an allowlist (exception chain, frames with source of in-app code, message, request method + path, runtime/os/browser names, breadcrumbs, non-sensitive tags, related log bodies, issue history), never from the raw event; kept free text goes through `redact` (IPs, URL hosts, emails, credentials, JWTs, home directories → placeholders). `prompt_test.go` lists what must never leak; extend it when adding a field.
- `internal/retention`: `Cleaner` runs at startup and every 10 minutes (started in main, stopped before the database closes): deletes events older than `RETENTION_EVENTS` (by `received_at`) and logs older than `RETENTION_LOGS` (by `timestamp`), keeps the newest `RETENTION_EVENTS_PER_ISSUE` events per issue (`event_count` still counts all; trimmed as each event is saved through `NewEvent.KeepEvents`, and by the cleaner when the limit is lowered), and above `MAX_DATABASE_SIZE` deletes the oldest events and logs together in time order down to 90% (batch sized from the average record). Each issue keeps its latest event (`notLatestEvent` in every delete), so every error stays listed with its count and last stack trace; if the database is still over the limit with only those left, a warning is logged. Logs of the same message (`grouping.LogFingerprint`: text with numbers/IDs replaced, column `logs.fingerprint`, migration 12) keep their newest `RETENTION_LOGS_PER_MESSAGE` (default 50): trimmed as they are saved (`SaveLogs` with the project's limit, so a logging loop replaces its old copies at once) and by the cleaner when the limit is lowered; logs from before the column have `''` and are limited by time and size only. Issues not seen for `RETENTION_ISSUES` (default a year, by `last_seen`) are deleted with their events. Store side in `store/retention.go`: deletes go in batches so ingest is never blocked long; the database uses incremental auto_vacuum (switched once with a VACUUM at open) and `ReleaseFreeSpace` gives freed pages back to the file system in steps of 2000 pages (each its own transaction). Trims go through indexes: `TrimIssueEvents` only visits issues with `event_count` over the limit, `TrimLogMessages` only messages over it (`trimMessage`, which repeats `fingerprint != ''` so the partial index `logs_by_fingerprint` is used); expiring issues lose their events in batches before the issue rows go. Every limit but the size can be overridden per project (`config.RetentionOverride`, nil = global; `Retention.For`): `Cleaner.groups` runs one `store.ProjectScope` per distinct setting plus one for every other project (including deleted ones) with the global values. The Projects page shows the size and the settings.
- `internal/projects`: `Registry` keeps the projects (table `projects`, migration 10): `Open` seeds `PROJECTS` at every start (`store.SeedProject`: created if missing, name and key set to the env values, retention from the UI kept; a name or key taken by another id stops startup), then caches the list in memory (`List`, reloaded after every change). Projects from env (`FromEnv`) can only change their retention in the UI and cannot be deleted; projects added in the UI get a generated 32-hex key, are fully editable, and `Delete` removes their issues, events, logs and connection entries. UI: `ui/controllers/projects.go`, `projects.html` (storage on top, then a table), `project.html` (`/projects`, `/projects/new`, `/projects/{id}`, `/projects/{id}/delete`). Each project has a color (migration 11; `''` follows `config.ProjectPalette` by id, choosing the palette color again stores `''`; `config.ValidColor` accepts only `#rrggbb`): the CSP forbids inline styles, so `Registry.Colors` builds a stylesheet (`[data-project="name"] { --project-color }`) served at `/project-colors.css?v=<hash>` (login required, it names projects) and every project and level is rendered with the one `badge` partial (`lists.Badge`): `projectBadge`/`levelBadge`/`statusBadge` make links (pass the list's `FilterLinks` inside the issue and log lists to filter that list; elsewhere they open `/issues` with that project or level, log levels named as event levels), `label "kind" name` plain labels (inside checkboxes), and chips set `RemoveURL` for the ×. A project badge (`data-project`) is an outlined badge in the project color (no fill, so it differs from level badges; first letter capitalized by CSS). Emails get `Notification.ProjectColor`; `projectColor` validates it for the inline style. Project and level filters take several values (`?project=a&project=b`, `?level=error&level=fatal`; `ProjectIDs`/`Levels` in `IssueFilter` and `LogFilter`): the `picker` partial (`lists.Picker`/`lists.Option`) is the one dropdown of checkboxes (`.picker`, no library: Select2 needs jQuery, Tom Select/Choices.js would need restyling and do not work without JS) whose field shows only the count ("Projects: 2"), kept in sync by app.js; in the active filters the chosen values share one chip (`filterField.badges`), each badge with its own ×.
- `internal/compact`: `Event` drops what does not help a fix before an event is stored: source and vars of library frames when the stack has in-app frames (grouping then uses only in-app frames, so it is unaffected), `modules`, `debug_meta`, `sdk.integrations`/`packages`, breadcrumbs beyond the newest 50.
- `internal/scrub`: removes credentials from SDK payloads before they are parsed or stored (ingest calls it), so the panel, the API, notifications and the database never hold the session cookies or tokens of the monitored app's users. Key-name based (`IsSensitiveKey`: password, token, auth, cookie, session, api key, …; `[name, value]` pairs too; log attributes keep their `{value, type}` shape) plus Bearer/Basic credentials and sensitive query parameters in strings. Data stored before it existed is not rewritten.
- Levels to record: each project may set its own event and log levels (`projects.event_levels`/`log_levels`, migration 13; NULL = the `Recording` defaults, '' = none; the form stores the defaults as NULL so a project follows them). `StoreSink` stores levels under their canonical names (`config.EventLevel`: critical = fatal, warn = warning, log = info, trace = debug, unknown = error; `config.LogLevel` for logs), so filters, notifications and badges never translate them again, and drops events and logs of levels not recorded before storing, so they never notify either.
- `internal/ingest`: `POST /api/{projectID}/envelope/`. Order matters: CORS → public key (query `sentry_key`, `X-Sentry-Auth`/`Authorization`, or the envelope header `dsn` when sent via a tunnel) → project auth → per-project rate limit → read/decompress body (gzip, deflate; 20 MB cap before and after decompression) → `scrub.JSON` on every event and log item, then `compact.Event` on events → parse all items → `Sink`. All items are parsed before anything is stored, so a malformed item rejects the whole envelope. Only `event` and `log` items reach the `Sink`; other types are dropped. `StoreSink` computes the grouping fingerprint and maps Sentry types to `store.NewEvent`/`store.NewLog`. Rejections are logged at debug level (ingest is public, so warn-level logging would be a flood vector).

### Projects and DSNs

`PROJECTS=1:backend:<key>,2:frontend:<key>` — `id:name:public_key`, seeded into the database at every start (more projects can be added in the UI, see `internal/projects`). IDs are chosen by the user and must stay stable: the id is part of the DSN (`http://<key>@host:8000/<id>`) and is stored with every event, so it must never be derived from list order. Each service (backend, SSR, frontend…) gets its own project; all live in one container and the UI shows which project an error came from. The Projects page shows each DSN: at `PUBLIC_URL` when set (path prefix kept), else at the address the UI was opened with (https behind a trusted proxy that sends `X-Forwarded-Proto`). The scheme is part of the DSN; SDKs cannot parse one without it.

Auth model: one admin from env (UI) and an API token, plus an IP allowlist for the UI and API; the ingest endpoint stays open (protected only by DSN keys, CORS `ALLOWED_ORIGINS` and rate limiting) because browsers send errors directly.

## Conventions

- Tests sit next to the code (`*_test.go`, same package unless they drive the whole server); fixtures go in `testdata/`. When adding a check, make sure the test fails without the fix.
- Blank lines (enforced by `wsl` in `.golangci.yml`, same rule as the team's TypeScript projects): always a blank line before `if`/`for`/`switch`/`defer`/`return`, including `if err != nil` right after the call; consecutive assignments stay together. Run `make fix` after editing; `--fix` only adds blank lines, it never removes extra ones.
- Everything in the repo is in English: code, comments, test data, UI text. Test values are plain and conventional (`root` / `root-password`, `admin`), not invented strings in other languages.
- Use descriptive variable names (`settings`, `database`, `transaction`, `migrationList`), not one-letter ones. Keep the standard Go idioms `err`, `ctx`, `t`, and `w`/`r` in HTTP handlers.
- Do not copy code from Bugsink (PolyForm Shield license) or Sentry (FSL). GlitchTip (MIT) is fine as a reference.
- Commit messages: one subject line containing `DevFo-OSS/17`, no body, no AI attribution. Commit only when asked.
- Keep the README abstract (goals and features). Implementation details are added only once the corresponding stage lands.

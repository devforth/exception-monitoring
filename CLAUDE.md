# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Lightweight self-hosted error and log monitoring server that accepts data from the official Sentry SDKs via DSN (envelope protocol). Go, embedded SQLite (`modernc.org/sqlite`, no CGO), shipped mainly as a Docker image (`FROM scratch`, size budget 50 MB, currently ~20 MB, ~6 MB to pull). MIT, public DevForth OSS project. Tracklify task: `DevFo-OSS/17`.

Scope: errors and logs only. Tracing spans, session replay, uptime and `client_report` items are accepted and dropped, not stored.

Stages: 0 protocol research, 1 skeleton, 2 ingest, 3 data model and grouping, 4 REST API, 5 UI (htmx) and 6 notifications (Slack and Telegram short, email full), 7 retention, 8 packaging and docs, and 9 MCP are done, plus users with roles and the issue status history. Next: the first release (tag `v0.1.0`).

## Commands

Go is installed in `~/.local/go`; if `go` is not on PATH, run `export PATH="$HOME/.local/go/bin:$HOME/go/bin:$PATH"` first.

```sh
make test         # go test -race ./...
make lint         # golangci-lint (.golangci.yml): vet, staticcheck, errcheck, gofmt/goimports, wsl blank lines
make fix          # auto-fix formatting, import order and blank lines; run after editing Go code
make build        # static binary to bin/exception-monitoring
make docker       # build image devforth/exception-monitoring:dev
make image-size   # fails if the image is over MAX_IMAGE_MB (50)

go test ./internal/storage/store -run TestNewerSchemaRejected -count=1   # single test
node --check internal/ui/views/static/app.js                     # Go tests do not run the JS
```

Do not start the server (`make run`, `docker run`, …) yourself; the user runs it in their own terminal. Check it with `curl localhost:8000/health` and ask the user to start it if it is not reachable. `make run` loads `.env` and `.env.local` (gitignored; template in `.env.example`); without projects (`PROJECTS` or added in the UI) every event is rejected, which is only visible with `LOG_LEVEL=debug`. `.env.example` holds placeholders only; the real keys and passwords go into `.env.local`. `go run` does not rebuild on change: after editing code (templates, CSS and JS are embedded too), the user must restart it.

The image has a writable `/tmp` (scratch has none): SQLite needs it for temporary files (VACUUM, building the search index) and otherwise fails with "disk I/O error (6410)". CI (`.github/workflows/ci.yml`) runs golangci-lint (pinned version), `make test`, an amd64 image build with the size check and an arm64 build. `release.yml` runs on a `vX.Y.Z` tag: it calls `ci.yml` (`workflow_call`), then pushes `devforth/exception-monitoring:X.Y.Z`, `:X.Y` and `:latest` (not for pre-releases) for amd64 and arm64 to Docker Hub (secrets `DOCKERHUB_USERNAME`, `DOCKERHUB_TOKEN`). `compose.yml` is the example deployment the docs refer to.

## Architecture

`internal/` is grouped by area; a package sits in the folder of the part it belongs to:

- `platform/`: what every part uses: `config` (with the field limits and the level order, `HighestFirst`/`InLevelOrder`), `logging`, `secret`, `text` (`TruncateRunes`, `EmailLocalPart`).
- `server/`: the HTTP shell (routes, health) with `access` (IP allowlist, token) and `httpjson`.
- `ingest/`: receiving from Sentry SDKs (handler, `StoreSink`) with `sentry` (wire format), `scrub`, `compact`, `grouping`.
- `storage/`: `store` (SQLite, migrations), `projects` (registry), `retention`.
- `notify/`: notifications.
- `api/`: the request catalog and its transports: `catalog`, `rest`, `mcp`, `oauth` (MCP sign-in), `agentprompt`.
- `services/`: the rules of the application, the only way the UI and the agents' tools reach the database (see below).
- `ui/`: the web UI. `fixtures/`: test data for tests only.

- `cmd/exception-monitoring/main.go`: loads config, opens the store, binds the listener before logging "server started", graceful shutdown on SIGTERM. The `healthcheck` subcommand is what Docker's HEALTHCHECK calls (no curl in a scratch image); `reset-password [username]` (the superadmin by default) prints a temporary password, the way to recover a forgotten one (`docker exec`); `version` prints the build version.
- `internal/platform/config`: everything comes from env (`APP_NAME` (default "Exception Monitoring": the sidebar, page titles, login, emails, the MCP server's title and instructions, `<name> MCP: get_issue …` in notifications and on issue pages; `config.AppSlug` turns it into the name agents register (`acme-errors`), with `exception-monitoring` when no Latin letter or digit is left; the database file itself is fixed, `Config.DatabaseFile()` = `DATA_DIR/database.db`, so renaming the app keeps the data), `PORT`, `DATA_DIR`, `LOG_LEVEL`, `LOG_FORMAT` (`internal/platform/logging`: `auto` = pretty, colored lines in a terminal, fields one per line for settings (`logging.Block`, used by the startup records) or when a line is wider than the terminal (`NO_COLOR` turns colors off), logfmt text elsewhere such as Docker; or `pretty`/`text`/`json`), `PROJECTS`, `ALLOWED_ORIGINS`, `RATE_LIMIT_PER_MINUTE`, `API_TOKEN`, `ALLOWED_IPS`, `TRUSTED_PROXIES`, `ADMIN_USERNAME`, `ADMIN_PASSWORD`, `SESSION_LIFETIME` (default `1d`, how long a UI login lasts; not extended by use), and the notification settings in `notifications.go`: `PUBLIC_URL`, `SECRET_KEY`, `SMTP_*`, `EMAIL_FROM`, `NOTIFY_RETRY_FOR`, `NOTIFY_KEEP_SENT`, `NOTIFY_KEEP_FAILED`; levels to record in `recording.go`: `RECORD_EVENT_LEVELS` (default error,fatal), `RECORD_LOG_LEVELS` (default all; `nil` list = every level, empty = none); retention in `retention.go`: `RETENTION_EVENTS`, `RETENTION_LOGS`, `RETENTION_EVENTS_PER_ISSUE`, `RETENTION_LOGS_PER_MESSAGE`, `RETENTION_ISSUES`, `MAX_DATABASE_SIZE` ("2GB"), 0 turns a limit off; list values in env are comma-separated strings, parsed once here into slices). `Notifications.ChannelAvailable(type)` says whether a connection type can be created and what is missing (email needs SMTP, Telegram/Slack need the secret key, which the server always has; unknown types are refused). `Load()` wraps `loadFrom(getenv)` so tests inject a map instead of touching the process env. `config.Projects` has `Find(idOrName)` and `ByID(id)`; use them instead of looping over projects. Code that needs the projects takes a `config.ProjectList` (`List()`) and asks on every use, because projects change while the server runs; a fixed `config.Projects` satisfies it in tests.
- `internal/storage/store`: `Open(ctx, path)` takes the database file (tests use `filepath.Join(t.TempDir(), "test.db")`). SQLite with WAL (`journal_size_limit` 64 MB, so the file shrinks back after a burst), `busy_timeout`, `foreign_keys`, and `_txlock=immediate`, which prevents "database is locked" on concurrent read-then-write transactions (there is a test for it).
  - Migrations live in the `migrations` slice in `migrate.go`: versions are sequential from 1, each runs in its own transaction, and an applied migration is never edited (add a new one, backfilling existing rows if needed). Startup refuses a database whose schema is newer than the binary.
  - Tables: `issues` (one per `project_id` + `fingerprint`, with status, `event_count`, `first_seen`/`last_seen`), `events` (unique `project_id` + `event_id`, so SDK retries are ignored; full JSON in `payload`; `trace_id`, `span_id`, `parent_span_id`), `logs` (`trace_id`, `span_id`, attributes JSON), `users` (migrations 17–18: username unique in any case, name, role `superadmin`/`admin`/`user` with at most one superadmin by a partial unique index, salted PBKDF2 `password_hash` (`pbkdf2-sha256$iterations$salt$key`, `services.HashPassword`; never read with a `store.User`, only by `FindLogin`/`UserPassword` where a password is checked), `must_change_password`, `last_login_at`; what each role may do is the methods of `store.User`: `CanAdminister`, `CanManage`, `CanAccessAgentsOf`, `AssignableRoles`, `Actor`), `sessions` (UI logins of a user, deleted with the user), `issue_status_changes` (every status change: from, to, `user_id` (SET NULL on delete) plus `user_name` kept, `source` ui/mcp/api/event, `event_id` of a reopening event; `SetIssuesStatus` takes a `store.Actor` and records only real changes with one `INSERT … SELECT` before the update, `SaveEvent` records a regression), `notification_outbox` (see notify; its `channel` column is the connection id), `notification_destinations` (where messages go: an email address, lowercase, with `verified`/`verified_at` and the code hash, expiry, attempts and `verify_sent_at`; or a chat with its encrypted secret), `notification_connections` (a rule: name, `destination_id`, all projects, levels, active; reading a connection joins the destination fields) + `notification_connection_projects`. A connection needs a confirmed destination; deleting a connection keeps the destination, so a confirmed address stays confirmed.
  - Times are fixed-width UTC TEXT (`timeFormat`) so they sort as strings; `first_seen`/`last_seen` use the server receive time, not the SDK clock.
  - `SaveEvent` reports `NewIssue`/`Regression` (a resolved issue that happened again goes back to unresolved; ignored stays ignored) for notifications.
  - `IssueFilter` date ranges apply to `DateField`: any event in range (default, an `EXISTS` on events), `first_seen` or `last_seen`. Only the API exposes the choice (`date_by`); the UI always uses any event in range (the sort already says which date matters).
  - The issue list as it opens and the unresolved count read `issues_by_status_last_seen` (migration 21). Logs filtered by level have no index on purpose: with several levels SQLite would read and sort every match, while the rowid scan stops after one page. Log counts (the pager) stop at `store.LogCountLimit` (10000; `CountLogs` returns `more`, the pager shows "of 10000+"), since an exact count reads every match.
  - Text search of logs (`log_search.go`) goes through `logs_search` (migration 22): an FTS5 trigram index that keeps neither the text (`content=''`) nor positions (`detail=none`), about the size of the text. `logQuery` asks it for every 3-character piece of the text (`searchMatch`: `"tim" AND "ime" AND ...`, at most 32) newest first, joins `logs` and checks `body LIKE` there, so a page or a capped count stops early whether the text is common or absent, and wildcards are searched as text. Text under 3 characters falls back to `body LIKE`, as do all searches while the index is being filled. Deleted logs stay in the index (removing them doubled the cost of deletes, and FTS5 gives the space back only by rewriting its largest segment, which held the write lock over 5 s): the join drops them, the LIKE check keeps a reused id from matching, a trigger counts them (`logs_search_backfill.stale`), and when they outnumber the live logs retention empties the index (`RefreshLogSearch`, under a second) for the background indexer to fill again. main's `indexLogSearch` runs for the server's life: it fills the index in batches (`IndexLogsForSearch`, progress `done_id`/`last_id`) and checks every minute for a refill.
  - Long background writes (retention, the indexer) rest `store.WritePause` (100 ms, `store.Pause`; loops of many small writes use `pacer`: 100 ms after every 200 ms of work) between their transactions: without it a waiting ingest write could not get the lock (SQLite's busy handler retries only every 100 ms) and failed with SQLITE_BUSY after `busy_timeout`. Measured on 4M logs: ingest waited at most 0.4 s while retention deleted 950k logs.
  - Trace and span columns have partial indexes (non-empty values only); SQLite uses one only when the query implies its condition, which a bound parameter never does, so every lookup on them goes through `indexedEquals`/`indexedIn`, which write the `!= ''` out (`plans_test.go` checks the plans).
  - API lists fetch `limit+1` rows; `store.Page` trims them and says whether a next page exists (cursor pagination). UI lists use pages instead: `IssueFilter`/`LogFilter` build their WHERE once (`where()`), shared by `ListIssues`/`ListLogs` and `CountIssues`/`CountLogs`.
  - `store` never imports `sentry`: callers map to `NewEvent`/`NewLog`.
- `internal/server`: `net/http` ServeMux with method patterns (`"GET /health"`), wrapped in a request-logging middleware. Built from `server.Options`; depends on small interfaces (`Pinger`, `http.Handler` for ingest, `Routes` for API and UI), so tests use fakes. Mounts ingest (open), `/health` (open), the API wrapped in `protectAPI` (IP allowlist first, then API token); MCP and UI use the IP allowlist plus their own authentication.
- `internal/server/access`: `ClientIP` (uses `X-Forwarded-For` only when the direct peer is in `TRUSTED_PROXIES`, read right to left), `FromTrustedProxy`, `RequireAllowedIP`, `RequireToken` (constant-time; empty `API_TOKEN` closes the REST API).
- `internal/server/httpjson`: `Write`/`Error` for JSON responses (`{"error": ...}`). Ingest keeps its own `writeError` because Sentry SDKs expect `{"detail": ...}` plus `X-Sentry-Error`.
- `internal/api/catalog` (package `catalog`): the one catalog of requests, served both as the REST API and as MCP tools (like AdminForth's endpoints → tools). `New(store, projects, services.All)` lists them in order (with nil arguments it only serves to read the definitions); each is `Define(Endpoint{Name, Description, ReadOnly, Idempotent, Destructive, Admin, RESTOnly, AgentsOnly}, handler)` with `handler(ctx, Call, In) (Out, error)`: the input schema comes from `In` (`json` + `jsonschema` tags, `jsonschema.For`), `Run` validates the input map against it and decodes it. A new tool or API route = one entry + its handler; nothing else to register. `Call` has the `Viewer` (the agent's user; `ByToken` for the REST token instead), the `Actor` (recorded in the history), `ForAgent` (`call.Text` redacts free text with `agentprompt.Redact` for agents, REST gets it as stored) and the server `Address` (DSNs). Output is JSON, or `catalog.Text` written as is (the agent prompt of `get_issue`/`get_event`). Errors: `Invalid(...)` (400 / tool error as is), `ErrNotFound`/`store.ErrNotFound` (404), anything else logged by the transport and reported as "internal error" (`Outcome`). Lists: `Page{items, next_cursor}`, 20 rows by default, at most 100, plain-number cursors (offset for issues/projects, last id for events/logs). `Run` refuses (as `ErrNotFound`) what `AllowedFor(call)` denies: the token runs everything but `AgentsOnly`, a user everything but `RESTOnly` and, without `CanAdminister`, `Admin`. `RESTOnly`: `get_event_payload` (raw payload), `list_trace` (log attributes). `AgentsOnly` (`manage.go`, `notifications.go`): account, agents, projects, users, notification connections and email confirmation, acting as the user through `services.All` (the same services as the UI, built by `services.New`, which check what the user may change; their `ErrForbidden` is reported as not found); form rules are shared because tools pass the form's fields as `url.Values` to `services.Projects.Save`/`Connections.Save`, starting from `FormValues` of the stored record so fields not given keep their values. Never tools: changing your own password (the UI asks for the current one) and generating personal tokens. A `Destructive` tool's description (`ToolDescription`) tells the agent to get an explicit confirmation in chat.
- `internal/api/rest` (package `rest`): serves the catalog under `/api/v1/<name>` behind `protectAPI`: `GET` with query parameters when `ReadOnly` (converted with `Endpoint.FieldType`; lists repeated or comma-separated; unknown parameters 400), `POST` with a JSON object otherwise (`api.Route`). Routes are registered one by one (a `/api/v1/` subtree would overlap `/api/{projectID}/envelope/`); any other `/api/` address answers a JSON 404 "unknown API endpoint". Actor "API token" (`store.SourceAPI`).
- `internal/api/mcp`: MCP server for coding agents at `/mcp` (official `github.com/modelcontextprotocol/go-sdk`, Streamable HTTP, stateless, JSON responses; the SDK's localhost protection is off because a reverse proxy on the same host would trip it, and a token is required anyway). Behind `ALLOWED_IPS`, then `oauth.Protect` (OAuth access token or the personal token; `API_TOKEN` is the REST API's only). Tools are the catalog of `internal/api/catalog` an agent's user may use, plus `fetch_skill` (agent only, `skills.go`), registered with `Server.AddTool` and the endpoint's schema: one `sdk.Server` per role, built at startup; `withCaller` (after `oauth.Protect`) reads the grant's user from the store at every request, so a role change applies at once, and puts the `catalog.Call` into the context, which picks the server and reaches the tool handlers. `list_issues`, `get_issue` (latest or given event as the full agent prompt, `agentprompt.Build(services.AgentInput(...))` with up to 20 related logs), `get_issues` and `update_issue_status` (1–100 IDs, `store.NormalizeIssueIDs`; the update is atomic, a missing ID changes nothing; recorded in the history as the grant's user: the call's `Actor` is the grant's user, found through `oauth.GrantOf(auth.TokenInfoFromContext(...))`, since `oauth.Protect` hands the grant to the SDK as its `auth.TokenInfo`), `list_issue_events`, `get_event`, `list_logs` (`trace_id` for one request), `list_projects` (with each project's `dsn`: `withCaller` puts the server address, `access.PublicURL`, into `Call.Address` and `config.Project.DSN` builds it, the same function as the Projects page), `fetch_skill`. Output goes to the agent's model provider: calls have `ForAgent`, so list text goes through `agentprompt.Redact`, and raw payloads and log attributes are never returned. `instructions.md` (sent with every connection, kept short) gives the workflow and lists the skills; `skills/*/SKILL.md` are loaded on demand by `fetch_skill` (fixed-name allowlist), one topic each, no rule repeated between them and the instructions. Notifications carry `<APP_NAME> MCP: get_issue {"issue_id":N}` (`notify.mcpReference`, built by `agentprompt.MCPReference`). `mcp_test.go` connects the SDK client over HTTP to the full server.
- `internal/api/oauth`: how agents sign in to MCP. OAuth 2.1 for public clients: discovery (`/.well-known/oauth-protected-resource`, `oauth-authorization-server` and `openid-configuration`, each with or without the MCP path), client identification by a Client ID Metadata Document (`clientmetadata.go`, as in AdminForth: a `client_id` that is an https URL is the client's published JSON with its name and redirect_uris, fetched at every authorization and never stored; the fetch reaches only public addresses, checked after DNS resolution in the dialer's `Control`, no redirects, 5 s, 5 KB; the consent page shows the publishing host; `Server.MetadataClient` points tests at a local server) or dynamic registration (`POST /oauth/register`; clients that never connected go after an hour, and a full table (1024) evicts the oldest unused instead of refusing; the code carries the client name, migration 20, so the token exchange needs neither), the consent page `GET/POST /oauth/authorize` (served by the UI: login, then Allow/Deny with a form token bound to the session and the exact request; its CSP `form-action` admits the agent's redirect origin via `middleware.ContentSecurityPolicy`), `POST /oauth/token` (code + S256 PKCE; refresh). Access tokens last an hour, refresh tokens 30 days and are replaced at every use; a spent refresh token presented again (theft) revokes the grant (`oauth_spent_refresh_tokens`, migration 16). Redirects: https or loopback http, matched exactly except a loopback port. Codes and tokens are random 32 bytes, stored only as SHA-256 hashes; nothing is kept in memory, and one `oauth.Server` built in main is shared by MCP and the UI. Registration and token requests are rate limited per address, the client table is capped, and browser requests must come from the server's own origin. A grant is a connected agent or a personal token (one per user, shown once after Generate/Regenerate) and acts for a user (`agent_grants.user_id`, from the code of the user who allowed it; a grant without a user does not work, and those from before users existed are given to the superadmin at startup, `store.AdoptAgents`). Deleting a user or a password reset by someone else disconnects their agents; changing your own password keeps them. The UI page `/agents` ("MCP" in the menu) has Claude Code / Codex / Other tabs, the viewer's personal token (right after Generate/Regenerate also "Copy setup prompt": a prompt that has an agent add the server with that token at user level and check it with `list_projects`, `presenters.setupPrompt`), the connected apps with Disconnect (admins choose whose apps with a select, `?user=`), and a warning when agents would reach the server over plain HTTP from another machine (`Server.Unencrypted`).
- `internal/services`: non-HTTP logic and every database access of the UI pages and the agents' tools (package `catalog`), built together by `services.New` (`services.All`); it imports nothing from `ui/`. `Issues` (list/count/get, recent events, `SelectedEvent`, actions, related logs, agent prompt), `Logs` (list/count, issues of logs), `Projects` (names, DSN, color, unresolved counts, database size; `Get`/`Save`/`Delete` and `FormValues`, the project form's rules in `project_form.go`), `Connections` (list, delivery health, get, `Save` (create or update from the form, `connection_form.go`: rule fields, chat secrets, availability, the confirmed address, duplicates, default name), `New` (a new connection's defaults), `FormValues`, `SetActive`/`SendTest` (`store.ErrNotVerified` for an unconfirmed address), `TestChat`, `RetryNow`, `Delete`), `Deliveries` (the outbox for the delivery log), `Verification` (email destinations, `StartEmail`/`ResendCode`/`ConfirmCode`, codes, `ResendCooldown`), `Users` (`EnsureSuperadmin`, create with a temporary password, update, reset password, delete, own name; each checks the viewer's role and returns `ErrForbidden`), `Agents` (`Page`: whose agents to list and the viewer's token state; disconnect, consent). `services.New` builds them all (`services.All`) for the controllers and for the request catalog, so pages and agents' tools apply the same rules. Package tests use a real temp database.
- `internal/ui`: web UI, server-rendered `html/template` + htmx. One source for each type: every view type (page data, rows, forms) is defined once, in `contracts`. Sub-packages by role (imports go down this list, never up):
  - `ui` (root): only the composition root, `New` (same signature as before) and `Register`; its full-server tests live in `ui/tests` (see Test data and tools).
  - One rule for data access: controllers never use `store` (the `Controllers` struct has no store field, so the compiler enforces it): all data access goes through services, and a change of several steps (a chat destination plus its connection, a replaced secret plus the save, find-or-create an email destination) is one service method.
  - `helpers`: pure formatting, no HTTP (`TimeAgo`, `LevelClass`, `CleanLog`, `PrettyJSON`, `KeptFor`, `RetentionDifferences`, …); imported by all.
  - `lists`: list machinery shared by pages and templates: `CleanListQuery`, `FilterLinks` and chips, `Badge` builders, `Picker`/`Option`, `Pager`/`ReadPaging`, `DateRange`, levels highest first (`EventLevels`, `LogLevels`).
  - `contracts`: view types and their display methods (`IssuesData`, `IssueData`, `LogsData`, `ProjectView`, `ConnectionView`, `DeliveriesView`, `LoginData`, `RequestInfo`, `UsersData`, `UserForm`, `AccountData`, …; the logged-in user is a `store.User`, not a view type); of the ui packages it imports only `lists` and `helpers`; the results of services it shows (`EmailStep`, `Duplicate`, `ChatTest`, `UserInput`) are `services` types (`services/results.go`). `limits.go` holds the limits of form fields (name lengths, the username pattern, code digits), checked by the server and given to templates by the `limits` function for maxlength/minlength/pattern, so they never differ.
  - `views`: embeds `views/templates` and `views/static`, the FuncMap (keys are what templates call), asset versions, the page wrapper `view` and `Renderer` (`Render`, `RenderFragment`, `RenderPartial`, `ServerError`). It takes the project colors as a small interface (`views.ProjectColors`, satisfied by `projects.Registry`).
  - `presenters`: store/config values → `contracts` types, no I/O (it uses the types of store and services but never calls them): issue/log/delivery rows, `Connections` (list rows with status, the form and its email step state, the form shown again, defaults of a new connection), `Projects` (table rows, the form with level options and retention placeholders), `Storage`. Read-only settings come as fields (notification settings, retention/recording defaults, `ProjectName`, `FromEnv`, `Color`), so tests build them from plain values.
  - `session`: the login of the web UI, `session.Auth` (sessions of users, `SessionUser`, `ChangePassword` (own password: the current one counts against the login limit), `Login` returning `LoginOK`/`LoginWrongCredentials`/`LoginBlocked` with the login limit inside, `IsHTTPS`), the limit on failed logins per address and per username, the form tokens of pages. Passwords are checked by `services.Users` (`Authenticate`, which checks unknown usernames against a dummy hash, and `ChangeOwnPassword`); the password primitives stay private to `services`, so nothing outside it can set a password without the role checks of `Users`.
  - `requests`: what a request carries about HTTP itself: bulk issue IDs, `ReadUser`, `IsHTMX`, `SafeNext` (local redirect targets only: control characters, spaces and backslashes refused, since browsers drop tabs and read `\` as `/`), the viewer. Forms whose rules agents share (projects, connections) are read by services from `url.Values`: the UI passes `r.PostForm`, a tool its input under the same field names.
  - `middleware`: `RequireLogin` (puts the user, a `store.User`, in the request: `requests.Viewer`, `$.Viewer` in templates), `RequirePasswordChanged` (a temporary password leads to the account page), `RequireAdmin` (a 404 page otherwise), `WithSession`, `SameOrigin`, `SecurityHeaders`, `StaticCache`.
  - `controllers`: the handlers, HTTP only (read the request via requests, call services, build the view with presenters, render), one file per page (`issues.go`, `actions.go`, `logs.go`, `projects.go`, `connections.go`, `email.go`, `deliveries.go`, `auth.go`, `users.go`, `account.go`, `agents.go`, `authorize.go`, `assets.go`) on one `Controllers` struct.
  - `routes`: the route table in four groups: `public` (login, logout), `account` (`RequireLogin` only: the one page open with a temporary password), `dashboard` (+ `RequirePasswordChanged`, any role) and `admin` (+ `RequireAdmin`: project settings, notifications, users), plus `/` for any other address (the 404 page, `WithSession` so logged-in users keep the menu; the REST API answers its own JSON 404 for `/api/`). Missing records and whatever a role may not open answer the same 404 page (`Controllers.NotFoundPage`, `views.NotFound`: centered, "Back to issues"), so users do not learn what exists; every POST of any group gets `SameOrigin` (CSRF) automatically, so new routes cannot forget either.
  - Copy buttons are the `copy-button` partial: `copyButton target label title copied` copies a textarea's value or an element's text, `copyText text label title copied` copies the text it carries (one per list row); without a label it is an icon. app.js shows the toast `#copy-status` of the layout. The issue list (columns: checkbox, ID, issue, …; the row shows the status: `tr.issue-unresolved` red tint, `tr.issue-resolved` green, `tr.issue-ignored` faded (on the `tr`); every `table.list` stripes its even rows with the `--stripe` overlay, so it works over any row color, its meaning in the title from the `status-title` partial) and page show the issue ID and copy its MCP request (`agentprompt.MCPReference`, the same text notifications carry).
  - Pages below a list link back with the `back` partial (`{{template "back" (back "/projects" "Projects")}}`); app.js follows it on Esc unless a dropdown, dialog or date picker is open or a field has focus.
  - `layout.html`: the menu has two groups, Monitoring (Issues with the count of unresolved issues, `views.IssueCounter` = `services.Issues.Unresolved`, asked on every full page; Logs) and Settings (Projects, Notifications and Users for admins, MCP last); the viewer's name links to `/account` above Log out. It is a sticky sidebar on the left (a bar at the top under 800px wide, icons only), the page beside it. The toggle collapses it to icons; app.js stores the choice in the `em_sidebar` cookie and the server renders the next page that way (`view.SidebarCollapsed`), so it does not jump on load.

- `internal/ingest/sentry`: the SDK wire format only (envelope splitting, `Event`, `Log`), no HTTP or storage. Decoding is deliberately lenient: custom types (`Timestamp`, `Message`, `Tags`, `ExceptionList`, …) accept every shape the protocol allows and fall back to the zero value on an unexpected one, because losing a field is better than losing the error report. `Event.Raw` keeps the full payload; `Event.Trace()` gives trace and span IDs; `NormalizeEventID` turns UUID form into 32 hex.
- `internal/ingest/grouping`: decides which events are one issue. Custom SDK `fingerprint` wins (`{{ default }}` expands to the default). Default: exception chain types + in-app frames as file/module + function + source line (`context_line`), no line numbers; in-app is `sentry.Frame.IsInApp`: marked by the SDK and not under `node_modules/` (a browser SDK marks every frame of the page's origin in-app, and Vite serves libraries from there as `/node_modules/.vite/deps/`), and only frames after the newest async boundary count (a function with `*`, e.g. Firefox's `promise callback*queueFlush`), so the path that scheduled the callback does not split one error into several issues (JS names `handler: () => {}` after the property, so the function name alone merges unrelated errors); anonymous functions without source use the line number; file and module paths drop origins, query strings (`tsx watch` adds `?<timestamp>`) and bundle hashes; if no frame has source code (browser), the normalized error text is added. Messages group by text with numbers/UUIDs/hex replaced. The package comment documents the rules; change grouping only with tests, because a change regroups new events into new issues.
- `internal/platform/secret`: AES-256-GCM `Box` keyed by `SECRET_KEY` (SHA-256 of the string); encrypts chat tokens and webhook URLs stored in the database. Without `SECRET_KEY`, main uses `secret.KeyFile(DATA_DIR)`: `secret.key` generated at the first start (0600, written whole via a temp file and a link, a damaged one stops startup instead of being replaced).
- `internal/notify`: alerts about new and regressed issues (`SaveEvent` reports them; `StoreSink` calls `Notify` with the project id). Destinations are **connections** stored in the database and managed on the UI Notifications page: type (email/telegram/slack), address or encrypted secret, projects (or all, including future ones), levels, active. Delivery goes through the `notification_outbox` table, so it survives restarts and outages:
  - `Notify` only queues in memory and never blocks ingest. A dispatcher goroutine reads the connections, sends each notification to those that match (`matches`: active, verified, project, level; unknown levels count as errors), applies the flood limit per connection (5 per minute individually, the rest as one `Summary` when the window ends; a window keeps only the count and the first `maxSummaryItems` held notifications, so a flood of large events does not pile up in memory) and writes outbox rows.
  - One worker goroutine per connection (started on demand, and at startup for connections with pending rows) sends due rows in order, so a destination stuck in retries (an SMTP provider rate-limiting; the free Mailtrap sandbox takes about one email per few seconds) does not delay the others. The channel is rebuilt from the stored connection for every attempt, so UI edits apply to queued messages; a disabled or deleted connection fails them (`errGone`). Retries follow `Schedule` (2s, 10s, 30s, 1m, 5m, 15m, 30m, then hourly) until `NOTIFY_RETRY_FOR`; `RetryAfterError` carries a channel's own rate-limit delay. Saving an active connection in the UI makes its waiting messages due at once (`store.RetryOutboxNow`, called from `services.Connections`), since a save is usually the fix; a "Retry now (N)" button (`retry-now` partial, `POST /notifications/{id}/retry`) does the same without a save, on the notifications list and the connection page while messages wait for a retry; the worker picks them up on its next poll (`PollInterval`, 1s). Every failed attempt is logged as a warning, giving up as an error.
  - A cleanup goroutine deletes sent rows after `NOTIFY_KEEP_SENT` and failed ones after `NOTIFY_KEEP_FAILED`.
  - `Close` on shutdown writes the in-memory queue and pending summaries to the outbox and sends what is due; rows waiting for a retry are sent after the next start. Only a killed process loses the in-memory part.
  - `Factory` builds channels from connections (decrypting secrets with the `Box`), sends test messages (`SendTest`) and is shared with the UI. Channels implement `Send`/`SendSummary`: `Slack` (incoming webhook, `{"text"}`, also Mattermost/Rocket.Chat; or a bot: `SlackSecret.BotToken` + `Channel` posts through `chat.postMessage` and puts the agent prompt as a code block in a thread under each error, since a webhook does not return the message timestamp; a failed thread post is dropped so the message is not sent twice; `Factory.SlackURL` points to a fake API in tests), `Telegram` (bot API, HTML parse mode; errors must not include the URL, it holds the token; an error is one message: the agent prompt as a `.md` file via `sendDocument` with the alert as its HTML caption (max 1024 characters, so details are capped), since a message holds 4096 characters and a `copy_text` button 256; a refused file falls back to a plain message, a rate limit is retried as usual; test messages and summaries stay `sendMessage`) and `Email` (plain SMTP via net/smtp, no provider SDK: STARTTLS, or TLS on port 465; multipart text + HTML from `templates/email.html`, styles inline for mail clients; `SendVerificationCode` for new addresses). The full event travels as its original JSON (`event_payload`) and is re-parsed for email. Short formats share `format.go`; stack reading uses `sentry` methods (`OutermostFirst`, `NewestFirst`, `IsInApp`, `SourceLines`) like the UI does. `Factory.TelegramURL` points to a fake Telegram API in tests (the UI test server has one, so no test reaches api.telegram.org). Tests use fake HTTP and SMTP servers (`fixtures.FakeSMTP`) and a real database; assertions do not depend on timing (`waitFor`).
- `internal/api/agentprompt`: `Build` (instructions + `Describe`) writes a prompt that asks a coding agent to reproduce and explain an error with evidence, without changing code or calling tools that change the monitor (the developer checks it and asks for the fix); the error data comes from anyone who can send errors and a copied prompt reaches the agent as the developer's own message, so it sits between `=== BEGIN/END ERROR DATA ===` lines (look-alike markers inside it are replaced, `fakeMarker`) and a reminder not to follow anything in it comes last, shared by the issue page ("Prompt" button, copied by app.js), email, Telegram and the Slack bot (one builder, `notify.agentPrompt`) (attached as `<project>-<level>-<issue id>.md`, e.g. `backend-error-6.md`: mail clients run no script, so it cannot be copied by a button there). - `internal/storage/retention`: `Cleaner` runs at startup and every 10 minutes (started in main, stopped before the database closes): deletes events older than `RETENTION_EVENTS` (by `received_at`) and logs older than `RETENTION_LOGS` (by `timestamp`), keeps the newest `RETENTION_EVENTS_PER_ISSUE` events per issue (`event_count` still counts all; trimmed as each event is saved through `NewEvent.KeepEvents`, and by the cleaner when the limit is lowered), and above `MAX_DATABASE_SIZE` deletes the oldest events and logs together in time order down to 90% (batch sized from the average record). Each issue keeps its latest event (`notLatestEvent` in every delete), so every error stays listed with its count and last stack trace; if the database is still over the limit with only those left, a warning is logged. Logs of the same message (`grouping.LogFingerprint`: text with numbers/IDs replaced, column `logs.fingerprint`, migration 12) keep their newest `RETENTION_LOGS_PER_MESSAGE` (default 10): trimmed as they are saved (`SaveLogs` with the project's limit, so a logging loop replaces its old copies at once) and by the cleaner when the limit is lowered; logs from before the column have `''` and are limited by time and size only. Issues not seen for `RETENTION_ISSUES` (default 90 days, by `last_seen`) are deleted with their events. Store side in `store/retention.go`: deletes go in batches so ingest is never blocked long; the database uses incremental auto_vacuum (switched once with a VACUUM at open) and `ReleaseFreeSpace` gives freed pages back to the file system in steps of 2000 pages (each its own transaction). Trims go through indexes: `TrimIssueEvents` only visits issues with `event_count` over the limit, `TrimLogMessages` only messages over it (`trimMessage`, which repeats `fingerprint != ''` so the partial index `logs_by_fingerprint` is used); expiring issues lose their events in batches before the issue rows go. Every limit but the size can be overridden per project (`config.RetentionOverride`, nil = global; `Retention.For`): `Cleaner.groups` runs one `store.ProjectScope` per distinct setting plus one for every other project (including deleted ones) with the global values. Every such section is built the same way: the `section-heading` partial (title and hint), then a `.section-values` span with what is set inside, shown on the line under the title (defaults muted, `ProjectView.RetentionSummary`). app.js keeps it in sync with the fields (`data-summary-of` for checkboxes, `data-summary-field` for inputs). - `internal/ingest/compact`: `Event` drops what does not help a fix before an event is stored: source and vars of library frames (not `IsInApp`, so `node_modules` too) when the stack has in-app frames (grouping then uses only in-app frames, so it is unaffected), `modules`, `debug_meta`, `sdk.integrations`/`packages`, breadcrumbs beyond the newest 50.
- `internal/ingest/scrub`: removes credentials from SDK payloads before they are parsed or stored (ingest calls it), so the panel, the API, notifications and the database never hold the session cookies or tokens of the monitored app's users. Key-name based (`IsSensitiveKey`: password, token, auth, cookie, session, api key, …; `[name, value]` pairs too; log attributes keep their `{value, type}` shape) plus Bearer/Basic credentials and sensitive query parameters in strings. - `internal/ingest`: `POST /api/{projectID}/envelope/`. Order matters: CORS → public key (query `sentry_key`, `X-Sentry-Auth`/`Authorization`, or the envelope header `dsn` when sent via a tunnel) → project auth → per-project rate limit → read/decompress body (gzip, deflate; 20 MB cap before and after decompression) → `scrub.JSON` on every log item and, for events, `prepareEvent` (`scrub.Value` and `compact.EventFields` in one JSON pass; `prepare_test.go` checks it gives what two passes gave) → parse all items → `Sink`. All items are parsed before anything is stored, so a malformed item rejects the whole envelope. Only `event` and `log` items reach the `Sink`; other types are dropped. `StoreSink` computes the grouping fingerprint and maps Sentry types to `store.NewEvent`/`store.NewLog`. Rejections are logged at debug level (ingest is public, so warn-level logging would be a flood vector).

### Projects and DSNs

`PROJECTS=1:backend:<key>,2:frontend:<key>` — `id:name:public_key`, seeded into the database at every start (more projects can be added in the UI, see `internal/storage/projects`). IDs are chosen by the user and must stay stable: the id is part of the DSN (`http://<key>@host:8000/<id>`) and is stored with every event, so it must never be derived from list order. Each service (backend, SSR, frontend…) gets its own project; all live in one container and the UI shows which project an error came from. The Projects page shows each DSN: at `PUBLIC_URL` when set (path prefix kept), else at the address the UI was opened with (https behind a trusted proxy that sends `X-Forwarded-Proto`). The scheme is part of the DSN; SDKs cannot parse one without it.

Auth model: users with roles (the superadmin from env at the first start, the others added in the UI) and an API token, plus an IP allowlist for the UI and API; the ingest endpoint stays open (protected only by DSN keys, CORS `ALLOWED_ORIGINS` and rate limiting) because browsers send errors directly.

## Conventions

- Tests sit next to the code (`*_test.go`, same package unless they drive the whole server); fixtures go in `testdata/`. When adding a check, make sure the test fails without the fix.
- Blank lines (enforced by `wsl` in `.golangci.yml`, same rule as the team's TypeScript projects): always a blank line before `if`/`for`/`switch`/`defer`/`return`, including `if err != nil` right after the call; consecutive assignments stay together. Run `make fix` after editing; `--fix` only adds blank lines, it never removes extra ones.
- Everything in the repo is in English: code, comments, test data, UI text. Test values are plain and conventional (`root` / `root-password`, `admin`), not invented strings in other languages.
- Use descriptive variable names (`settings`, `database`, `transaction`, `migrationList`), not one-letter ones. Keep the standard Go idioms `err`, `ctx`, `t`, and `w`/`r` in HTTP handlers.
- Do not copy code from Bugsink (PolyForm Shield license) or Sentry (FSL). GlitchTip (MIT) is fine as a reference.
- Commit messages: one subject line containing `DevFo-OSS/17`, no body, no AI attribution. Commit only when asked.
- `skills/exception-monitoring/SKILL.md`: the Agent Skills skill for users' coding agents (`npx skills add devforth/exception-monitoring -g`, or `~/.claude/skills/`, `~/.agents/skills/`): deploy, connect MCP, connect an app, investigate. It holds the workflow and safety rules and links the docs by raw GitHub URL instead of repeating them; a change to a documented step updates the doc, and the skill only when the workflow changes.
- Field hints: a `?` next to a settings field (`{{template "hint" (fieldHelp "Notifications" "Chat ID")}}`, or `settingHelp "RETENTION_EVENTS"` for a field that overrides a variable) shows the description from the table row of `docs/ui.md` (by `## section` and field label) or `docs/configuration.md`, embedded by the `docs` package; never write the text in a template. A missing row fails the page, so the full-server tests catch it. Obvious fields (names, passwords) get no hint. `.dockerignore` must keep the embedded docs.
- Docs: the README is short (features, quick start, one SDK example, links); user docs are in `docs/` (`deployment.md`, `configuration.md` with every env var, `ui.md` with the fields of the settings pages, `sdk.md`, `mcp.md`, `api.md`) and `docs/sentry-protocol.md` is research notes. A new or changed env var, subcommand, API route or MCP tool updates its doc in the same change, and `.env.example` too.

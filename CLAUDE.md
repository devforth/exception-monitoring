# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Lightweight self-hosted error and log monitoring server that accepts data from the official Sentry SDKs via DSN (envelope protocol). Go, an embedded key-value store (goleveldb, pure Go, no CGO), shipped mainly as a Docker image (`FROM scratch`, size budget 50 MB, currently ~20 MB, ~6 MB to pull). MIT, public DevForth OSS project. Tracklify task: `DevFo-OSS/17`.

Scope: errors and logs only. Tracing spans, session replay, uptime and `client_report` items are accepted and dropped, not stored.

Stages: 0 protocol research, 1 skeleton, 2 ingest, 3 data model and grouping, 4 REST API, 5 UI (htmx) and 6 notifications (Slack and Telegram short, email full), 7 retention (now cleanup by size), 8 packaging and docs, and 9 MCP are done, plus users with roles and the issue status history. Next: the first release (tag `v0.1.0`).

## Commands

Go is installed in `~/.local/go`; if `go` is not on PATH, run `export PATH="$HOME/.local/go/bin:$HOME/go/bin:$PATH"` first.

```sh
make test         # go test -race ./...
make lint         # golangci-lint (.golangci.yml): vet, staticcheck, errcheck, gofmt/goimports, wsl blank lines
make fix          # auto-fix formatting, import order and blank lines; run after editing Go code
make build        # static binary to bin/exception-monitoring
make docker       # build image devforth/exception-monitoring:dev
make image-size   # fails if the image is over MAX_IMAGE_MB (50)

go test ./internal/storage/database -run TestUserRules -count=1   # single test
node --check internal/ui/views/static/app.js                     # Go tests do not run the JS
```

Do not start the server (`make run`, `docker run`, …) yourself; the user runs it in their own terminal. Check it with `curl localhost:8000/health` and ask the user to start it if it is not reachable. `make run` loads `.env` and `.env.local` (gitignored; template in `.env.example`); without projects (`PROJECTS` or added in the UI) every event is rejected, which is only visible with `LOG_LEVEL=debug`. `.env.example` holds placeholders only; the real keys and passwords go into `.env.local`. `go run` does not rebuild on change: after editing code (templates, CSS and JS are embedded too), the user must restart it.

The image has a writable `/tmp` (scratch has none). CI (`.github/workflows/ci.yml`) runs golangci-lint (pinned version), `make test`, an amd64 image build with the size check and an arm64 build. `release.yml` runs on a `vX.Y.Z` tag: it calls `ci.yml` (`workflow_call`), then pushes `devforth/exception-monitoring:X.Y.Z`, `:X.Y` and `:latest` (not for pre-releases) for amd64 and arm64 to Docker Hub (secrets `DOCKERHUB_USERNAME`, `DOCKERHUB_TOKEN`). `compose.yml` is the example deployment the docs refer to.

## Architecture

Where to look first:

| What | Where |
|---|---|
| Startup, shutdown, subcommands | `cmd/exception-monitoring/main.go` |
| Every periodic job and its lane | `cmd/exception-monitoring/jobs.go`; the runner `internal/platform/background` |
| Schedules, time limits, size limits | `internal/platform/config/schedule.go`, `retention.go` |
| All settings from env | `internal/platform/config` (documented in `docs/configuration.md`) |
| HTTP mounts (health, ingest, API, MCP, OAuth, UI) | `internal/server/server.go`; UI routes in `internal/ui/routes` |
| REST endpoints and MCP tools | `internal/api/catalog` (one entry each) |
| Rules of the application | `internal/services` (the only way UI and tools reach data) |
| Storage records and their rules | `internal/storage/store`; every collection and index in `internal/storage/database/schema.go` |
| Ingest path | `internal/ingest` (handler → inbox → pipeline → `StoreSink`) |
| Notifications | `internal/notify` |

`internal/` is grouped by area; a package sits in the folder of the part it belongs to:

- `platform/`: what every part uses: `config` (with the field limits and the level order, `HighestFirst`/`InLevelOrder`), `logging`, `secret`, `text` (`TruncateRunes`, `Shorten` with "…", `ContainsFold` (case-insensitive substring, the log search), `EmailLocalPart`).
- `server/`: the HTTP shell (routes, health) with `access` (IP allowlist, token) and `httpjson`.
- `ingest/`: receiving from Sentry SDKs (handler, `StoreSink`) with `sentry` (wire format), `scrub`, `compact`, `grouping`.
- `storage/`: `store` (the API of the storage: the records, their rules and the `Store` interface, the one list of every operation; everything else uses only it), `database` (the one implementation of that API: every record, the ingest inbox included, each collection declared in `database/schema.go`; the engine is picked in `database/engine_leveldb.go`, the only file naming it, and its data lives in `DATA_DIR/leveldb`), `kv` (the layer under it, unaware of the application: keys built from typed parts, collections with declared indexes, batches with counters and sequence numbers, queries and cursors (`Head` decodes only a record's head when the collection has `DecodeHead`, as events do; `Raw` filters on the stored bytes before decoding; `Count` without `Where` counts keys), `Check`, the `Engine` interface; nothing else builds a key), `kv/leveldb` (the goleveldb adapter, the only code importing goleveldb, checked by `kv/adapters_test.go`; goleveldb is pure Go, so the binary stays static and the image `FROM scratch`, and its files are LevelDB's format, so a LevelDB C++ adapter could read them; it is unmaintained since 2022, a risk accepted for that; another store is another adapter package plus another `database/engine_<name>.go` under a build tag), `kv/enginetest` (the test every adapter must pass), `projects` (registry). Tests open a store with `storetest.Open(t)` (a `database` in a temporary directory); the measurements open a copy of a 60-day seed with `storetest.OpenSeed`. Ingest goes through `ingest.Pipeline` (inbox, processors, one writer that notifies after each batch). The rest of the code takes `store.Store`; only `main` and tests open the database.
- `notify/`: notifications.
- `api/`: the request catalog and its transports: `catalog`, `rest`, `mcp`, `oauth` (MCP sign-in), `agentprompt`.
- `services/`: the rules of the application, the only way the UI and the agents' tools reach the database (see below).
- `ui/`: the web UI. `fixtures/`: test data for tests only.

- `cmd/exception-monitoring/main.go`: loads config, sets a soft memory limit of 200 MiB unless `GOMEMLIMIT` is set (`config.LimitMemory`, `config.DefaultMemoryLimit`), opens the store, starts the periodic jobs of `jobs.go` (`lanes`, logged at start as "background jobs"; a lane runs its jobs one at a time, lanes side by side, stopped before the notifier and the store close; `TestJobsStartApart` checks no two start in the same minute over a day), binds the listener before logging "server started", graceful shutdown on SIGTERM. The `healthcheck` subcommand is what Docker's HEALTHCHECK calls (no curl in a scratch image); `reset-password [username]` (the superadmin by default) prints a temporary password, the way to recover a forgotten one (with the server stopped: `docker compose run --rm exception-monitoring reset-password`); `backup [absolute dir]` (default `DATA_DIR/backups/<time>`; `make backup` locally, `docker compose run --rm exception-monitoring backup` in Docker) (`backup.go`) asks the running server over its control socket (`internal/server/control`, `DATA_DIR/control.sock`, mode 0600, closed before the store) to write a backup, or opens the database itself when no server answers; `version` prints the build version.
- `internal/platform/config`: everything comes from env (`APP_NAME` (default "Exception Monitoring": the sidebar, page titles, login, emails, the MCP server's title and instructions, `<name> MCP: get_issue …` in notifications and on issue pages; `config.AppSlug` turns it into the name agents register (`acme-errors`), with `exception-monitoring` when no Latin letter or digit is left; the database directory is fixed, `DATA_DIR/leveldb`, so renaming the app keeps the data), `PORT`, `DATA_DIR`, `LOG_LEVEL`, `LOG_FORMAT` (`internal/platform/logging`: `auto` = pretty, colored lines in a terminal, fields one per line for settings (`logging.Block`, used by the startup records) or when a line is wider than the terminal (`NO_COLOR` turns colors off), logfmt text elsewhere such as Docker; or `pretty`/`text`/`json`), `PROJECTS`, `ALLOWED_ORIGINS`, `RATE_LIMIT_PER_MINUTE`, `API_TOKEN`, `ALLOWED_IPS`, `TRUSTED_PROXIES`, `ADMIN_USERNAME`, `ADMIN_PASSWORD`, `SESSION_LIFETIME` (default `1d`, how long a UI login lasts; not extended by use), and the notification settings in `notifications.go`: `PUBLIC_URL`, `SECRET_KEY`, `SMTP_*`, `EMAIL_FROM`, `NOTIFY_RETRY_FOR`, `NOTIFY_KEEP_SENT`, `NOTIFY_KEEP_FAILED`; levels to record in `recording.go`: `RECORD_EVENT_LEVELS` (default error,fatal), `RECORD_LOG_LEVELS` (default all; `nil` list = every level, empty = none); the size limit in `retention.go`: `MAX_DATABASE_SIZE` ("2GB", 0 turns it off), with the fixed numbers of the cleanup (`CleanupStartPercent`, `CleanupStopPercent`, `CleanupAge`, `OldEventsPerIssue`, `LogsPerMessage`); list values in env are comma-separated strings, parsed once here into slices). `Notifications.ChannelAvailable(type)` says whether a connection type can be created and what is missing (email needs SMTP, Telegram/Slack need the secret key, which the server always has; unknown types are refused). `Load()` wraps `loadFrom(getenv)` so tests inject a map instead of touching the process env. `config.Projects` has `Find(idOrName)` and `ByID(id)`; use them instead of looping over projects. Code that needs the projects takes a `config.ProjectList` (`List()`) and asks on every use, because projects change while the server runs; a fixed `config.Projects` satisfies it in tests.
- `internal/storage/store` and `internal/storage/database`: the records and their rules are in `store` (`store.Store` lists every operation); `database` stores them on the `kv` layer, every collection declared once in `database/schema.go` (keys, indexes, byte counters). `database.Open(DATA_DIR)` opens `DATA_DIR/leveldb`; the running server holds it, so `reset-password` runs with the server stopped. `Store.Backup` (`database/backup.go`) copies a snapshot key by key (`kv.Copy`) into a new engine in a temporary directory inside the target, with `secret.key`, and renames the database into place last, so a backup is whole or absent while writes go on (the cleanup by size does not start meanwhile); `BackupStopped` does the same with the database opened read-only. There are no migrations: the format is recorded (`storeFormat` in `database/store.go`), and a database of another format, or without one, is refused at start with a message to move it away; a compatible change is a new collection or a field read with a default.
  - IDs: users, agents (grants), notification destinations and connections, and issues have 8 random characters `[a-z0-9]` (`store.NewID`, checked free in the batch that writes the record; `store.ValidID` refuses anything else before a lookup, routes answer 404). A project added in the UI gets a random 8-digit number (its id is in the DSN; `PROJECTS` sets its own). Event and log ids are sequence numbers (API cursors), outbox ids too.
  - Rules kept by indexes and batches: usernames unique in any case and one superadmin (unique indexes of `user`), one personal token per user, a refresh token of a client (`grant` indexes), project name and key unique; deleting a user removes their sessions, codes and grants in the same batch, deleting a connection its queued messages, deleting a project its place in connections, then its issues and logs in batches. A batch reads stored keys only (`kv.Batch.Iterate`), so deleting while walking is safe.
  - Users: salted PBKDF2 `password_hash` (`pbkdf2-sha256$iterations$salt$key`, `services.HashPassword`) kept beside the user, never returned with a `store.User`, only by `FindLogin`/`UserPassword` where a password is checked; what each role may do is the methods of `store.User`: `CanAdminister`, `CanManage`, `CanAccessAgentsOf`, `AssignableRoles`, `Actor`. Sessions are keyed by the hash of the cookie.
  - Issue status changes: from, to, the actor (user id and name kept; source ui/mcp/api/event) and `event_id` of a reopening event; `SetIssuesStatus` records only real changes, `SaveEvent` records a regression.
  - Notification destinations (an email address, lowercase, with `Verified`/`VerifiedAt`/`VerifySentAt` (`store.Destination`) and the code hash, expiry and attempts (`destinationRecord`); or a chat with its encrypted secret) and connections (a rule: name, destination, all projects or their ids, levels, active; reading one fills the destination fields). A connection needs a confirmed destination; deleting a connection keeps the destination, so a confirmed address stays confirmed. The outbox channel of a message is its connection's id.
  - `first_seen`/`last_seen` use the server receive time, not the SDK clock; the times of events and logs are the SDK's, moved by the device's clock drift when the envelope's `sent_at` is a minute or more from the receive time (`ingest.clockDrift`, applied in `parseItems`; the event page says how far the clock was off, `IssueData.ClockDrift`). `SaveEvent` reports `NewIssue`/`Regression` (a resolved issue that happened again goes back to unresolved; ignored stays ignored) for notifications.
  - Issues are kept in memory as well (`issueTable`), so issue lists filter and sort there (`issueOrder`, ties by id); `IssueFilter` date ranges apply to `DateField`: any event in range (default), `first_seen` or `last_seen` (only the API exposes the choice, `date_by`). Issues sort by last seen, first seen, events or project; random ids have no order to sort by.
  - Logs and events are read newest first through their indexes; time marks (`marks.go`) turn date ranges into sequence ranges. Text search of logs compares each line (`text.ContainsFold`), first on the stored bytes when the text has no character JSON escapes (`rawSearchable`), so most lines are never decoded; a count that the index walks answer exactly counts keys (`countByKeys`); log counts (the pager) stop at `store.LogCountLimit` (10000; `CountLogs` returns `more`, the pager shows "of 10000+").
  - API lists fetch `limit+1` rows; `store.Page` trims them and says whether a next page exists (cursor pagination). UI lists use pages (`Offset`/`Limit` of `IssueFilter`/`LogFilter`); issues are filtered in memory (`filterIssues`, shared by `ListIssues` and `CountIssues`), logs by walking an index newest first.
  - `store` never imports `sentry`: callers map to `NewEvent`/`NewLog`.
- `internal/server`: `net/http` ServeMux with method patterns (`"GET /health"`), wrapped in a request-logging middleware. Built from `server.Options`; depends on small interfaces (`Pinger`, `http.Handler` for ingest, `Routes` for API and UI), so tests use fakes. Mounts ingest (open), `/health` (open; 503 when `Store.Ping`, a read of the store, fails), the API wrapped in `protectAPI` (IP allowlist first, then API token); MCP and UI use the IP allowlist plus their own authentication.
- `internal/server/access`: `ClientIP` (uses `X-Forwarded-For` only when the direct peer is in `TRUSTED_PROXIES`, read right to left), `FromTrustedProxy`, `RequireAllowedIP`, `RequireToken` (constant-time; empty `API_TOKEN` closes the REST API).
- `internal/server/httpjson`: `Write`/`Error` for JSON responses (`{"error": ...}`). Ingest keeps its own `writeError` because Sentry SDKs expect `{"detail": ...}` plus `X-Sentry-Error`.
- `internal/api/catalog` (package `catalog`): the one catalog of requests, served both as the REST API and as MCP tools (like AdminForth's endpoints → tools). `New(projects, services.All)` lists them in order; handlers reach data only through `services.All` (no store), so tools and pages apply the same rules (with nil arguments it only serves to read the definitions); each is `Define(Endpoint{Name, Description, ReadOnly, Idempotent, Destructive, Admin, RESTOnly, AgentsOnly}, handler)` with `handler(ctx, Call, In) (Out, error)`: the input schema comes from `In` (`json` + `jsonschema` tags, `jsonschema.For`), `Run` validates the input map against it and decodes it. A new tool or API route = one entry + its handler; nothing else to register. `Call` has the `Viewer` (the agent's user; `ByToken` for the REST token instead), the `Actor` (recorded in the history), `ForAgent` (`call.Text` redacts free text with `agentprompt.Redact` for agents, REST gets it as stored) and the server `Address` (DSNs). Output is JSON, or `catalog.Text` written as is (the agent prompt of `get_issue`/`get_event`). Errors: `Invalid(...)` (400 / tool error as is), `ErrNotFound`/`store.ErrNotFound` (404), anything else logged by the transport and reported as "internal error" (`Outcome`). Lists: `Page{items, next_cursor}`, 20 rows by default, at most 100, plain-number cursors (offset for issues/projects, last id for events/logs). `Run` refuses (as `ErrNotFound`) what `AllowedFor(call)` denies: the token runs everything but `AgentsOnly`, a user everything but `RESTOnly` and, without `CanAdminister`, `Admin`. `RESTOnly`: `get_event_payload` (raw payload), `list_trace` (log attributes). `AgentsOnly` (`manage.go`, `notifications.go`): account, agents, projects, users, notification connections and email confirmation, acting as the user (the services check what the user may change; their `ErrForbidden` is reported as not found); form rules are shared because tools pass the form's fields as `url.Values` to `services.Projects.Save`/`Connections.Save`, starting from `FormValues` of the stored record so fields not given keep their values. Never tools: changing your own password (the UI asks for the current one) and generating personal tokens. A `Destructive` tool's description (`ToolDescription`) tells the agent to get an explicit confirmation in chat.
- `internal/api/rest` (package `rest`): serves the catalog under `/api/v1/<name>` behind `protectAPI`: `GET` with query parameters when `ReadOnly` (converted with `Endpoint.FieldType`; lists repeated or comma-separated; unknown parameters 400), `POST` with a JSON object otherwise (`rest.Route`). Routes are registered one by one (a `/api/v1/` subtree would overlap `/api/{projectID}/envelope/`); any other `/api/` address answers a JSON 404 "unknown API endpoint". Actor "API token" (`store.SourceAPI`).
- `internal/api/mcp`: MCP server for coding agents at `/mcp` (official `github.com/modelcontextprotocol/go-sdk`, Streamable HTTP, stateless, JSON responses; the SDK's localhost protection is off because a reverse proxy on the same host would trip it, and a token is required anyway). Behind `ALLOWED_IPS`, then `oauth.Protect` (OAuth access token or the personal token; `API_TOKEN` is the REST API's only). Tools are the catalog of `internal/api/catalog` an agent's user may use, plus `fetch_skill` (agent only, `skills.go`), registered with `Server.AddTool` and the endpoint's schema: one `sdk.Server` per role, built at startup; `withCaller` (after `oauth.Protect`) reads the grant's user from the store at every request, so a role change applies at once, and puts the `catalog.Call` into the context, which picks the server and reaches the tool handlers. `list_issues`, `get_issue` (latest or given event as the full agent prompt, `agentprompt.Build(services.AgentInput(...))` with up to 20 related logs), `get_issues` and `update_issue_status` (1–100 IDs, `store.NormalizeIssueIDs`; the update is atomic, a missing ID changes nothing; recorded in the history as the grant's user: the call's `Actor` is the grant's user, found through `oauth.GrantOf(auth.TokenInfoFromContext(...))`, since `oauth.Protect` hands the grant to the SDK as its `auth.TokenInfo`), `list_issue_events`, `get_event`, `list_logs` (`trace_id` for one request), `list_projects` (with each project's `dsn`: `withCaller` puts the server address, `access.PublicURL`, into `Call.Address` and `config.Project.DSN` builds it, the same function as the Projects page), `fetch_skill`. Output goes to the agent's model provider: calls have `ForAgent`, so list text goes through `agentprompt.Redact`, and raw payloads and log attributes are never returned. `instructions.md` (sent with every connection, kept short) gives the workflow and lists the skills; `skills/*/SKILL.md` are loaded on demand by `fetch_skill` (fixed-name allowlist), one topic each, no rule repeated between them and the instructions. Notifications carry `<APP_NAME> MCP: get_issue {"issue_id":"k3x9q2mf"}` (`notify.mcpReference`, built by `agentprompt.MCPReference`). `mcp_test.go` connects the SDK client over HTTP to the full server.
- `internal/api/oauth`: how agents sign in to MCP. OAuth 2.1 for public clients: discovery (`/.well-known/oauth-protected-resource`, `oauth-authorization-server` and `openid-configuration`, each with or without the MCP path), client identification by a Client ID Metadata Document (`clientmetadata.go`, as in AdminForth: a `client_id` that is an https URL is the client's published JSON with its name and redirect_uris, fetched at every authorization and never stored; the fetch reaches only public addresses, checked after DNS resolution in the dialer's `Control`, no redirects, 5 s, 5 KB; the consent page shows the publishing host; `Server.MetadataClient` points tests at a local server) or dynamic registration (`POST /oauth/register`; clients that never connected go after an hour, and a full table (1024) evicts the oldest unused instead of refusing; the code carries the client name, so the token exchange needs neither), the consent page `GET/POST /oauth/authorize` (served by the UI: login, then Allow/Deny with a form token bound to the session and the exact request; its CSP `form-action` admits the agent's redirect origin via `middleware.ContentSecurityPolicy`; it keeps the `Referrer-Policy: same-origin` of every page, so the agent never gets its address as a referrer while the form still sends its `Origin`, which `no-referrer` would turn into `Origin: null` and the CSRF check would reject), `POST /oauth/token` (code + S256 PKCE; refresh). Access tokens last an hour, refresh tokens 30 days and are replaced at every use; a spent refresh token presented again (theft) revokes the grant (collection `oauth_spent`). Redirects: https or loopback http, matched exactly except a loopback port. Codes and tokens are random 32 bytes, stored only as SHA-256 hashes; nothing is kept in memory, and one `oauth.Server` built in main is shared by MCP and the UI (through `services.Agents`). Registration and token requests are rate limited per address, the client table is capped, and browser requests must come from the server's own origin. A grant is a connected agent or a personal token (one per user, shown once after Generate/Regenerate) and acts for a user (the grant's user id, from the code of the user who allowed it; a grant without a user does not work). Deleting a user or a password reset by someone else disconnects their agents; changing your own password keeps them. The UI page `/agents` ("MCP" in the menu) has Claude Code / Codex / Other tabs, the viewer's personal token (right after Generate/Regenerate also "Copy setup prompt": a prompt that has an agent add the server with that token at user level and check it with `list_projects`, `presenters.setupPrompt`), the connected apps with Disconnect (admins choose whose apps with a select, `?user=`), and a warning when agents would reach the server over plain HTTP from another machine (`Server.Unencrypted`).
- `internal/services`: non-HTTP logic and every database access of the UI pages and the agents' tools (package `catalog`), built together by `services.New` (`services.All`), once in main and passed to `ui.New` and `catalog.New`; it imports nothing from `ui/`. `Issues` (list/count/get/get many, events, recent events, `SelectedEvent`, actions, related logs, agent prompt), `Logs` (list/count, issues of logs), `Projects` (names, DSN, color, unresolved counts, database size; `Get`/`Save`/`Delete` and `FormValues`, the project form's rules in `project_form.go`), `Connections` (list, delivery health, get, `Save` (create or update from the form, `connection_form.go`: rule fields, chat secrets, availability, the confirmed address, duplicates, default name), `New` (a new connection's defaults), `FormValues`, `SetActive`/`SendTest` (`store.ErrNotVerified` for an unconfirmed address), `TestChat`, `RetryNow`, `Delete`), `Deliveries` (the outbox for the delivery log), `Verification` (email destinations, `StartEmail`/`ResendCode`/`ConfirmCode`, codes, `ResendCooldown`), `Users` (`EnsureSuperadmin`, create with a temporary password, update, reset password, delete, own name; each checks the viewer's role and returns `ErrForbidden`), `Agents` (`Page`: whose agents to list and the viewer's token state; disconnect, consent). `services.New` builds them all (`services.All`) for the controllers and for the request catalog, so pages and agents' tools apply the same rules. Package tests use a real temp database.
- `internal/ui`: web UI, server-rendered `html/template` + htmx. One source for each type: every view type (page data, rows, forms) is defined once, in `contracts`. Sub-packages by role (imports go down this list, never up):
  - `ui` (root): only the composition root, `New` (it takes the `services.All` built in main) and `Register`; its full-server tests live in `ui/tests` (see Test data and tools).
  - One rule for data access: controllers never use `store` (the `Controllers` struct has no store field, so the compiler enforces it): all data access goes through services, and a change of several steps (a chat destination plus its connection, a replaced secret plus the save, find-or-create an email destination) is one service method.
  - `helpers`: pure formatting, no HTTP (`TimeAgo`, `LevelClass`, `CleanLog`, `PrettyJSON`, …); imported by all.
  - `lists`: list machinery shared by pages and templates: `CleanListQuery`, `FilterLinks` and chips, `Badge` builders, `Picker`/`Option`, `Pager`/`ReadPaging`, `DateRange`, levels highest first (`EventLevels`, `LogLevels`).
  - `contracts`: view types and their display methods (`IssuesData`, `IssueData`, `LogsData`, `ProjectView`, `ConnectionView`, `DeliveriesView`, `LoginData`, `RequestInfo`, `UsersData`, `UserForm`, `AccountData`, …; the logged-in user is a `store.User`, not a view type); of the ui packages it imports only `lists` and `helpers`; the results of services it shows (`EmailStep`, `Duplicate`, `ChatTest`, `UserInput`) are `services` types (`services/results.go`). `limits.go` gives templates the field limits of `config` (the `limits` function, for maxlength/minlength/pattern), so the forms and the server's checks never differ.
  - `views`: embeds `views/templates` and `views/static`, the FuncMap (keys are what templates call), asset versions, the page wrapper `view` and `Renderer` (`Render`, `RenderFragment`, `RenderPartial`, `ServerError`). It takes the project colors as a small interface (`views.ProjectColors`, satisfied by `projects.Registry`).
  - `presenters`: store/config values → `contracts` types, no I/O (it uses the types of store and services but never calls them): issue/log/delivery rows, `Connections` (list rows with status, the form and its email step state, the form shown again, defaults of a new connection), `Projects` (table rows, the form with level options), `Storage`. Read-only settings come as fields (notification settings, recording defaults, `ProjectName`, `FromEnv`, `Color`), so tests build them from plain values.
  - `session`: the login of the web UI, `session.Auth` (sessions of users, `SessionUser`, `ChangePassword` (own password: the current one counts against the login limit), `Login` returning `LoginOK`/`LoginWrongCredentials`/`LoginBlocked` with the login limit inside, `IsHTTPS`), the limit on failed logins per address and per username, the form tokens of pages. Passwords are checked by `services.Users` (`Authenticate`, which checks unknown usernames against a dummy hash, and `ChangeOwnPassword`); the password primitives stay private to `services`, so nothing outside it can set a password without the role checks of `Users`.
  - `requests`: what a request carries about HTTP itself: bulk issue IDs, `ReadUser`, `IsHTMX`, `SafeNext` (local redirect targets only: control characters, spaces and backslashes refused, since browsers drop tabs and read `\` as `/`), the viewer. Forms whose rules agents share (projects, connections) are read by services from `url.Values`: the UI passes `r.PostForm`, a tool its input under the same field names.
  - `middleware`: `RequireLogin` (puts the user, a `store.User`, in the request: `requests.Viewer`, `$.Viewer` in templates), `RequirePasswordChanged` (a temporary password leads to the account page), `RequireAdmin` (a 404 page otherwise), `WithSession`, `SameOrigin`, `SecurityHeaders`, `StaticCache`.
  - `controllers`: the handlers, HTTP only (read the request via requests, call services, build the view with presenters, render), one file per page (`issues.go`, `actions.go`, `logs.go`, `projects.go`, `connections.go`, `email.go`, `deliveries.go`, `auth.go`, `users.go`, `account.go`, `agents.go`, `authorize.go`, `assets.go`) on one `Controllers` struct.

- `internal/ingest/sentry`: the SDK wire format only (envelope splitting, `Event`, `Log`), no HTTP or storage. Decoding is deliberately lenient: custom types (`Timestamp`, `Message`, `Tags`, `ExceptionList`, …) accept every shape the protocol allows and fall back to the zero value on an unexpected one, because losing a field is better than losing the error report. `Event.Raw` keeps the full payload; `Event.Trace()` gives trace and span IDs; `NormalizeEventID` turns UUID form into 32 hex.
- `internal/ingest/grouping`: decides which events are one issue. Custom SDK `fingerprint` wins (`{{ default }}` expands to the default). Default: exception chain types + in-app frames as file/module + function + source line (`context_line`), no line numbers; events with the same fingerprint in one project are one issue, every exception of the chain adds its type and its frames (the in-app ones when there are any, otherwise all frames after the async boundary); line numbers are left out so a deploy that shifts code opens no new issue, and the source line keeps two throws in one function, or two functions with the same name, apart; in-app is `sentry.Frame.IsInApp`: marked by the SDK and not under `node_modules/` (a browser SDK marks every frame of the page's origin in-app, and Vite serves libraries from there as `/node_modules/.vite/deps/`), and only frames after the newest async boundary count (a function with `*`, as Firefox and Safari mark it, e.g. `promise callback*queueFlush`), so the path that scheduled the callback does not split one error into several issues (JS names `handler: () => {}` after the property, so the function name alone merges unrelated errors); anonymous functions without source use the line number; file and module paths drop origins, query strings (`tsx watch` adds `?<timestamp>`) and bundle hashes; if no frame has source code (browser), the normalized error text is added. An exception without frames adds its normalized value instead; messages (and `captureMessage`'s exception without a type) group by their normalized text, so "order 890" and "order 891" match. These rules and `docs/sdk.md` (Grouping) are the one description of grouping; change grouping only with tests, because a change regroups new events into new issues.

- `internal/ingest/scrub`: removes credentials from SDK payloads before they are parsed or stored (ingest calls it), so the panel, the API, notifications and the database never hold the session cookies or tokens of the monitored app's users. Key-name based (`IsSensitiveKey`: password, token, auth, cookie, session, api key, …; `[name, value]` pairs too; log attributes keep their `{value, type}` shape) plus Bearer/Basic credentials and sensitive query parameters in strings. A removed value becomes `[Filtered]` (`scrub.Filtered`); SDKs with `sendDefaultPii` send request cookies and the `Authorization` header, so the key rules apply to every part of a payload (headers, cookies, frame variables, breadcrumb data, extra, contexts, log attributes). It is one pass over the JSON tokens (`encoding/json/jsontext`, `Stream`/`Object`/`Values`), no tree; only an array led by a secret's name is read as a tree, so deep nesting stays linear (`TestDeepNestingStaysLinear`). - Levels to record: each project may set its own event and log levels (`Project.EventLevels`/`LogLevels`; nil = the `Recording` defaults, an empty list = none, kept apart through JSON by `keepNone`; the form stores the defaults as NULL so a project follows them). `StoreSink` stores levels under their canonical names (`config.EventLevel`: critical = fatal, warn = warning, log = info, trace = debug, unknown = error; `config.LogLevel` for logs), so filters, notifications and badges never translate them again, and drops events and logs of levels not recorded before storing, so they never notify either.
- `internal/ingest`: `POST /api/{projectID}/envelope/`. Order matters: CORS → public key (query `sentry_key`, `X-Sentry-Auth`/`Authorization`, or the envelope header `dsn` when sent via a tunnel) → project auth → per-project rate limit → read/decompress body (gzip, deflate; 20 MB cap before and after decompression) → the inbox (`Pipeline.accept`: the envelope as it came, with the project and the receive time; 429 above `config.MaxInboxBytes`, 20% of `MAX_DATABASE_SIZE`, so a backlog can never crowd out stored data) and the answer. A processor then runs `scrub.JSON` on every log item and, for events, `prepareEvent` (`compact.Event` over `scrub`'s token decoder and encoder, one pass; `prepare_test.go` checks, also as a fuzz target, that it gives what the tree pass it replaced gave) → parse all items → the writer's batch, which also deletes the inbox entry. All items are parsed before anything is stored, so a malformed item drops the whole envelope. Only `event` and `log` items reach the `Sink`; other types are dropped. Without a `Pipeline` (package tests) the handler parses the items and hands them to the `Sink` in the request. `StoreSink` computes the grouping fingerprint and maps Sentry types to `store.NewEvent`/`store.NewLog`. Rejections are logged at debug level (ingest is public, so warn-level logging would be a flood vector).

### Projects and DSNs

`PROJECTS=1:backend:<key>,2:frontend:<key>` — `id:name:public_key`, seeded into the database at every start (more projects can be added in the UI, see `internal/storage/projects`). IDs are chosen by the user and must stay stable: the id is part of the DSN (`http://<key>@host:8000/<id>`) and is stored with every event, so it must never be derived from list order. Each service (backend, SSR, frontend…) gets its own project; all live in one container and the UI shows which project an error came from. The Projects page shows each DSN: at `PUBLIC_URL` when set (path prefix kept), else at the address the UI was opened with (https behind a trusted proxy that sends `X-Forwarded-Proto`). The scheme is part of the DSN; SDKs cannot parse one without it.

Auth model: users with roles (the superadmin from env at the first start, the others added in the UI) and an API token, plus an IP allowlist for the UI and API; the ingest endpoint stays open (protected only by DSN keys, CORS `ALLOWED_ORIGINS` and rate limiting) because browsers send errors directly.

## Conventions

- Tests sit next to the code (`*_test.go`, same package unless they drive the whole server); fixtures go in `testdata/`. When adding a check, make sure the test fails without the fix.
- Blank lines (enforced by `wsl` in `.golangci.yml`, same rule as the team's TypeScript projects): always a blank line before `if`/`for`/`switch`/`defer`/`return`, including `if err != nil` right after the call; consecutive assignments stay together. Run `make fix` after editing; `--fix` only adds blank lines, it never removes extra ones.
- Everything in the repo is in English: code, comments, test data, UI text. Test values are plain and conventional (`root` / `root-password`, `admin`), not invented strings in other languages.
- Use descriptive variable names (`settings`, `database`, `batch`, `connectionList`), not one-letter ones. Keep the standard Go idioms `err`, `ctx`, `t`, and `w`/`r` in HTTP handlers.
- Do not copy code from Bugsink (PolyForm Shield license) or Sentry (FSL). GlitchTip (MIT) is fine as a reference.
- Commit messages: one subject line containing `DevFo-OSS/17`, no body, no AI attribution. Commit only when asked.
- `skills/exception-monitoring/SKILL.md`: the Agent Skills skill for users' coding agents (`npx skills add devforth/exception-monitoring -g`, or `~/.claude/skills/`, `~/.agents/skills/`): deploy, connect MCP, connect an app, investigate. It holds the workflow and safety rules and links the docs by raw GitHub URL instead of repeating them; a change to a documented step updates the doc, and the skill only when the workflow changes.
- Field hints: a `?` next to a settings field (`{{template "hint" (fieldHelp "Notifications" "Chat ID")}}`, or `settingHelp "MAX_DATABASE_SIZE"` for a variable) shows the description from the table row of `docs/ui.md` (by `## section` and field label) or `docs/configuration.md`, embedded by the `docs` package; never write the text in a template. A missing row fails the page, so the full-server tests catch it. Obvious fields (names, passwords) get no hint. `.dockerignore` must keep the embedded docs.
- Docs: the README is short (features, quick start, one SDK example, links); user docs are in `docs/` (`deployment.md`, `configuration.md` with every env var, `ui.md` with the fields of the settings pages, `sdk.md`, `mcp.md`, `api.md`) and `docs/sentry-protocol.md` is research notes. A new or changed env var, subcommand, API route or MCP tool updates its doc in the same change, and `.env.example` too.
